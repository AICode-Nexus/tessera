# v0.6 Subagent Approval Policy Core Helper Design

## Goal

Add core-owned, non-executing helpers for sub-agent approval-forwarding and inactive-child policy metadata. This keeps the next v0.6 slice inside the existing runtime ownership contract: `core` can validate and emit provider-neutral records, while child execution, automatic approval forwarding, scheduler loops, storage writes, tool execution, and workspace mutation remain blocked.

## Context

The current v0.6 foundation already has protocol events and client/GUI projection for:

- `subagent_approval_forwarding_recorded`
- `subagent_inactive_policy_recorded`
- `SubagentApprovalForwardingRecord`
- `SubagentInactivePolicyRecord`

`SubagentRuntimeCoordinator` also validates start/completion metadata and transcript artifact lifecycle records. The missing piece is a deterministic core helper for constructing approval-forwarding and inactive-policy records so future runtime slices do not invent this logic in CLI, TUI, GUI, provider, storage, or app-server code.

## Approaches Considered

### Recommended: Extend `SubagentRuntimeCoordinator`

Add two request types and four helper methods:

- `SubagentApprovalForwardingRequest`
- `SubagentInactivePolicyRequest`
- `record_approval_forwarding`
- `approval_forwarding_event`
- `record_inactive_policy`
- `inactive_policy_event`

This matches the existing runtime coordinator pattern for decisions and transcript lifecycle metadata. It keeps validation local, deterministic, and easy to test without broadening runtime powers.

### Alternative: Protocol-only contract

Leave existing protocol events as the only contract and let callers construct records directly. This is smaller, but it repeats validation rules in future entry points and weakens the core-owned runtime boundary.

### Alternative: Runtime-integrated approval forwarding

Start wiring approval forwarding into a real child-agent runtime. This is out of scope because automatic forwarding, inactive-child execution, child scheduling, and provider-backed sub-agent execution are still gated.

## Design

The slice adds core helper requests only; protocol event shapes stay unchanged. `SubagentApprovalForwardingRequest` contains the session descriptor, approval id, optional reviewer gate id, forwarding status, and reason. `SubagentInactivePolicyRequest` contains the session descriptor, inactive policy, parent action, and reason.

Validation remains intentionally narrow:

- `QueuedForReviewer` requires a reviewer gate id.
- `ForwardedToParent` requires an approval id and rejects sessions whose approval metadata says it was already forwarded from a parent.
- `DeniedByPolicy` preserves a reason and does not require a reviewer gate.
- `RequireReviewer` inactive policy must map to `RequireReviewer` or `PauseParent`.
- `QueueDecision` inactive policy must map to `QueueDecision`.
- `PauseParent` inactive policy must map to `PauseParent`.

The helpers return provider-neutral records or `RunEvent` values. They do not write storage, call providers, execute tools, mutate files, start background workers, or drive UI state.

## Data Flow

1. A future runtime component or test creates a `SubagentSessionDescriptor`.
2. The caller passes it to `SubagentRuntimeCoordinator` with an approval or inactive-policy request.
3. The coordinator validates metadata and returns a `SubagentApprovalForwardingRecord` or `SubagentInactivePolicyRecord`.
4. The event helper wraps the record in the existing `RunEvent` variant.
5. Existing client and GUI projections can consume the event without any new commands.

## Testing

Use TDD in `crates/core/tests/subagent_runtime_contract.rs`.

Tests should prove:

- queued approval forwarding requires a reviewer gate;
- forwarded-to-parent records preserve approval id and reviewer gate metadata;
- forwarded-to-parent rejects a session already marked as forwarded from parent;
- denied-by-policy events are metadata-only;
- inactive require-reviewer policy emits an event with reviewer-oriented parent action;
- mismatched inactive policy and parent action are rejected deterministically.

Targeted verification:

```bash
PATH="$HOME/.cargo/bin:$PATH" cargo test -p tessera-core subagent_approval_policy
```

Final verification remains the repository gate:

```bash
PATH="$HOME/.cargo/bin:$PATH" cargo fmt --all -- --check
PATH="$HOME/.cargo/bin:$PATH" cargo clippy --workspace --all-targets -- -D warnings
PATH="$HOME/.cargo/bin:$PATH" cargo test --workspace
git diff --check
```

## Boundaries

This slice must not implement:

- automatic approval forwarding;
- child-agent scheduling or execution;
- inactive-child runtime handling;
- provider calls;
- storage writes beyond future callers writing ordinary trace events;
- tool execution;
- workspace mutation;
- hooks, automations, app-server listener, MCP runtime, or swarm.
