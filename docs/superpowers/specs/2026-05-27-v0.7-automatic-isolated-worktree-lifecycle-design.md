# v0.7 Automatic Isolated Worktree Lifecycle Design

## Goal

Design the next conservative v0.7 slice after trace-driven apply-patch: an opt-in automatic isolated worktree lifecycle for `tessera apply-patch --from-trace`, so callers no longer have to pre-create and pass `--isolated-root`.

This is a worktree lifecycle gate, not a general Git automation gate. It may prepare and optionally clean up a detached isolated worktree for one reviewed apply-patch operation, but it must not stage, commit, push, open pull requests, run tests, restore checkpoints or expose GUI/TUI/app-server mutation controls.

## Current State

Tessera now has:

- provider-neutral coding workflow metadata for workflow scope, mutation request proposals, patch proposals, checkpoint lifecycle records, reviewer decisions, policy decisions, sandbox labels, patch artifacts, apply-patch preflight records and apply-patch execution records;
- `TraceApplyPatchResolver`, which resolves reviewed trace metadata into an apply envelope without reading artifact body bytes or mutating a workspace;
- `tessera apply-patch --from-trace`, which loads a clean patch artifact body, requires a caller-supplied non-primary isolated root, then reuses the shared apply-patch gate and executor;
- `ApplyPatchExecutor`, which can write one UTF-8 create/modify patch inside that caller-supplied isolated root after executor-ready checks.

Tessera still does not have:

- automatic worktree root preparation;
- deterministic root labels and lifecycle metadata for auto-created worktrees;
- source checkout cleanliness checks before creating a worktree;
- cleanup or retention policy for worktrees created by Tessera;
- test/lint runner integration;
- checkpoint creation or restore;
- Git stage/commit/push/PR mutation;
- GUI/TUI/app-server mutation controls.

## Design Decision

Add an explicit `--auto-worktree` mode to trace-driven apply-patch in a future implementation slice.

Recommended command shape:

```bash
tessera apply-patch \
  --from-trace trace_apply_patch_demo \
  --auto-worktree \
  --json
```

`--auto-worktree` is initially valid only with `--from-trace`. It is mutually exclusive with `--isolated-root` and `--root-label`; Tessera generates both. Explicit mode keeps requiring operator-supplied isolated root fields.

The automatic mode should:

1. resolve the trace-backed apply-patch bundle;
2. load and validate exactly one patch body source;
3. plan a deterministic isolated worktree label and path outside the source checkout by default;
4. verify the source checkout is safe to branch from;
5. create a detached Git worktree at the selected source commit;
6. run the existing apply-patch gate/executor against that worktree;
7. append lifecycle, preflight and execution metadata without storing absolute filesystem paths or patch bodies in trace;
8. retain or remove the worktree according to a conservative lifecycle policy.

## Command Shape

New options:

- `--auto-worktree`: create an isolated worktree automatically for trace-driven apply.
- `--worktree-base <path>`: optional base directory for generated worktrees. Default is under Tessera's data directory, not inside the source checkout.
- `--worktree-retention <policy>`: optional policy, initially `retain-on-success` by default.
- `--source-root <path>`: optional explicit source checkout root. Default is the current directory's Git root.

Retained existing options:

- `--from-trace <trace_id>`: required for automatic worktree mode.
- `--workflow-id`, `--request-id`, `--patch-id`, `--patch-artifact-id`: selectors only.
- `--patch-file` or `--stdin`: manual patch body override, still mutually exclusive with `--patch-artifact-id`.
- `--dry-run`: resolves and validates the bundle without creating a worktree by default.

Rejected combinations:

- `--auto-worktree` with explicit `--isolated-root` or `--root-label`;
- `--auto-worktree` without `--from-trace`;
- `--auto-worktree` with explicit-envelope proof flags such as `--checkpoint-id`, `--reviewer-gate-id`, `--policy-decision-id` or `--sandbox-profile`;
- `--auto-worktree --dry-run` creating a worktree as a side effect in the first implementation.

## Source Checkout Rules

Automatic mode must derive the source checkout from local operator context, not from trace payloads.

Default source root:

1. If `--source-root` is provided, canonicalize it and require it to be a Git worktree.
2. Otherwise use the Git root for the current process directory.
3. Reject non-Git directories.
4. Record only safe labels and commit metadata in trace, not absolute source paths.

Cleanliness:

- tracked modifications block automatic worktree creation;
- staged changes block automatic worktree creation;
- untracked files do not block by default because they are not copied into the new worktree, but CLI output should report that they were ignored;
- future `--strict-clean-source` may block untracked files too, but it is not required for the first slice.

Source commit:

- use the source checkout `HEAD` commit;
- create a detached worktree at that commit for the first implementation;
- do not create a branch by default, because branch creation is a broader Git namespace mutation;
- print the source commit in CLI output and record the commit hash in trace metadata.

## Worktree Directory And Label Policy

Default base directory:

```text
<data_dir>/worktrees/<repo-key>/
```

`repo-key` should be derived from safe local metadata, such as a normalized repository basename plus a short hash of the canonical source root. The hash is local metadata; trace should store only the key or path hash, not the absolute source path.

Generated worktree id and label:

```text
workspace_worktree_<uuid-or-short-hash>
worktree:<workflow-short>-<patch-short>
```

Rules:

- root label must never be `project`, `local` or empty;
- generated filesystem leaf names must be ASCII, path-safe and length-bounded;
- worktree paths must be under the selected base directory;
- if `--worktree-base` points inside the source checkout, Tessera must require that directory to be ignored by Git before creating anything;
- path collisions fail before mutation unless a future explicit reuse policy is designed.

## Lifecycle Metadata

Future implementation should add a provider-neutral lifecycle event instead of overloading apply-patch execution metadata.

Proposed event kind:

```text
workspace_worktree_lifecycle_recorded
```

Proposed statuses:

- `planned`
- `created`
- `creation_failed`
- `retained`
- `cleanup_started`
- `cleanup_completed`
- `cleanup_failed`

Proposed record fields:

- `worktree_id`
- `workflow_id`
- `task_id`
- `trace_id`
- `source_commit`
- `source_branch_label`
- `worktree_root_label`
- `worktree_base_key`
- `lifecycle_status`
- `reason`
- `created_for_request_id`
- `created_for_patch_id`
- `evidence`
- `metadata`

Trace payload must not include:

- absolute source root path;
- absolute worktree path;
- patch body text;
- old or new file contents;
- raw Git command strings;
- stdout/stderr bodies;
- API keys, cookies, authorization headers or other secrets.

CLI output may print the absolute worktree path because the local operator needs to inspect it, but replayable trace metadata should remain path-redacted.

## Runtime Flow

Automatic apply flow:

1. Resolve config and data directory.
2. Read and resolve `--from-trace` metadata with `TraceApplyPatchResolver`.
3. Load the clean patch artifact body or one explicit patch source.
4. Resolve source root and source commit from local operator context.
5. Plan worktree id, root label, base key and path.
6. Verify the source checkout has no tracked or staged modifications.
7. Append or prepare lifecycle metadata for `planned`.
8. Create a detached worktree at the source commit.
9. Append `workspace_worktree_lifecycle_recorded` with `created`.
10. Build the existing `CliApplyPatchEnvelope` with the generated isolated root and root label.
11. Run `ApplyPatchGate` and append `apply_patch_preflight_recorded`.
12. If executor-ready, run `ApplyPatchExecutor` and append `apply_patch_execution_recorded`.
13. Apply retention policy.
14. Print JSON/text output including trace id, worktree id, root label, worktree path, source commit, preflight status, execution status and cleanup/retention state.

Dry-run flow:

- resolve trace metadata and patch body;
- run dry-run/preflight semantics without creating a worktree;
- do not append worktree lifecycle events unless a future `--prepare-worktree` mode is explicitly designed.

## Retention And Cleanup Policy

Default policy: `retain-on-success`.

Recommended first policies:

- `retain-on-success`: retain worktree after a successful apply so the operator can inspect the diff.
- `cleanup-on-failure`: remove a worktree created by this invocation if apply never wrote changes or failed before executor execution.
- `retain-always`: retain even after failures for debugging.

Cleanup rules:

- never remove a worktree that was not created by the current invocation unless a future explicit cleanup command is designed;
- never use force removal by default;
- if cleanup fails because files changed or Git refuses removal, retain and report the path;
- append cleanup failure metadata without deleting user work;
- do not run `git clean`, `git reset`, `git checkout`, `git stash` or similar destructive commands.

## Safety Boundaries

Allowed for the future implementation slice:

- read local Git metadata from an operator-supplied or current source checkout;
- create one detached isolated worktree for one trace-driven apply operation;
- remove only an empty or unchanged worktree created by the same invocation under conservative cleanup rules;
- append worktree lifecycle metadata, apply-patch preflight metadata and apply-patch execution metadata;
- write one UTF-8 create/modify patch through the existing `ApplyPatchExecutor` inside the auto-created isolated root.

Not allowed:

- create branches by default;
- switch the primary checkout;
- write the primary checkout;
- run tests, linters or formatters;
- run `git apply`, system `patch`, shell pipelines or provider tools;
- create or restore checkpoints;
- stage, commit, push, pull, merge, rebase or open pull requests;
- delete user work or force-remove dirty worktrees;
- expose GUI/TUI/app-server mutation buttons;
- store absolute paths, patch bodies or file contents in trace.

## Architecture Boundary

Core should own lifecycle semantics and metadata construction. The future implementation may use an injected command runner for Git worktree operations so contract tests can cover behavior without shelling out by default.

CLI remains an entry point:

- parse flags;
- resolve config/data dir;
- supply source root and worktree base options;
- invoke core-owned lifecycle/apply orchestration;
- print local paths in process output.

Storage remains append-only JSONL plus rebuildable indexes. If a future cleanup command needs a local path registry, it must be designed separately and must not make SQLite the only event truth.

## Alternatives Considered

### Keep Manual `--isolated-root` Forever

Rejected. It preserves safety but leaves trace-driven apply too awkward for repeated coding-agent workflows.

### Create A Branch For Every Worktree

Rejected for the first slice. Branch creation is a Git namespace mutation and should wait until commit/stage/PR semantics are designed.

### Store Absolute Worktree Paths In Trace

Rejected. Trace must remain portable and must not leak local filesystem layout. CLI output can show local paths; trace stores labels, ids, commit metadata and path keys only.

### Run Tests Automatically After Applying

Rejected. Test runner policy integration is a separate v0.7 gate.

### Cleanup All Tessera Worktrees Opportunistically

Rejected. Broad cleanup risks deleting user inspection state. The first slice only cleans up worktrees created by the current invocation under conservative rules.
