# v0.6 Subagent Task Owner Bridge Design

## Goal

Add core-owned, non-executing helpers that bridge sub-agent session metadata to existing task ownership metadata. The helpers should construct `task_owner_attached` and `task_owner_detached` events for the sub-agent child task id without starting a child scheduler, calling providers, executing tools, writing storage, driving UI actions, or implying provider socket reattach.

## Context

The v0.5 task ownership foundation already has provider-neutral `TaskOwnerLease`, `TaskOwnerAttached`, `TaskOwnerDetached`, heartbeat, lost-owner, and reattach metadata. The v0.6 sub-agent foundation already records parent/child task linkage in `SubagentSessionDescriptor`, but the current `SubagentRuntimeCoordinator` only validates sub-agent runtime decisions, transcript artifact lifecycle, approval-forwarding, inactive-policy, and cancellation cascade metadata.

The next safe foundation slice is a deterministic bridge from a sub-agent session descriptor to child task owner metadata. This lets future runtime-capable work reuse the same ownership contract for child sessions while keeping the actual child runtime and scheduler blocked.

## Approaches Considered

### Recommended: Extend `SubagentRuntimeCoordinator`

Add request types and helper methods for child task owner attach and detach events:

- `SubagentTaskOwnerAttachRequest`
- `SubagentTaskOwnerDetachRequest`
- `task_owner_lease`
- `task_owner_attach_event`
- `task_owner_detach_event`

This keeps the mapping from sub-agent session metadata to task ownership metadata in `core`, next to the rest of the sub-agent runtime foundation.

### Alternative: Use `TaskOwnershipRecorder` directly

Callers could write task owner events with `TaskOwnershipRecorder`. That works for trace persistence, but it repeats sub-agent-specific validation in future entry points and risks CLI, TUI, GUI, provider, or storage code deciding child ownership rules.

### Alternative: Start executable child ownership

Attach execution owners as part of a real child runtime and scheduler. This is out of scope because provider-backed child execution, scheduler loops, automatic approval forwarding, inactive-child execution, and executable cancellation/reattach remain gated.

## Design

The slice adds a narrow bridge. `SubagentTaskOwnerAttachRequest` carries a session descriptor, trace id, runtime id, optional client id, requested owner kind, last trace sequence, heartbeat interval, and reason. The attach helper returns a `TaskOwnerLease`; the event helper wraps it in `RunEvent::TaskOwnerAttached`.

Validation:

- `child_task_id` is required.
- `trace_id` must be non-empty after trimming.
- `reason` must be non-empty after trimming.
- `heartbeat_interval_ms` must be greater than zero.
- `TaskOwnerKind::Execution` is allowed only for `SubagentSessionStatus::Active`.
- `TaskOwnerKind::Observer` is allowed for planned, active, waiting-for-approval, inactive, and handed-off sessions.
- Completed, failed, and cancelled sessions cannot attach a new owner.

`SubagentTaskOwnerDetachRequest` carries a session descriptor, lease id, and optional reason. Detach requires `child_task_id` and returns a `RunEvent::TaskOwnerDetached` for that child task id.

The helpers do not persist trace records. Future runtime code can choose whether to wrap them in `TaskOwnershipRecorder` or append the returned events through the standard core event path.

## Data Flow

1. A future runtime component or test has a `SubagentSessionDescriptor` with a child task id.
2. The caller creates an attach or detach request.
3. `SubagentRuntimeCoordinator` validates session status, child task linkage, and ownership metadata.
4. The coordinator returns a provider-neutral `TaskOwnerLease` or `TaskOwnerDetached` event.
5. Existing client, TUI, GUI, and runtime readers can project the standard task owner metadata.

## Testing

Use TDD in `crates/core/tests/subagent_runtime_contract.rs`.

Tests should prove:

- attach requires a child task id;
- active execution owner attach targets the child task id and preserves trace/runtime/client metadata;
- observer owner attach is allowed for waiting/inactive metadata-only sessions;
- execution owner attach is rejected for waiting/inactive sessions;
- terminal sessions cannot attach a new owner;
- detach event targets the child task id and preserves lease id and reason;
- attach events are metadata-only and do not include provider, tool, storage, scheduler, or UI payloads.

## Boundaries

This slice must not implement:

- child-agent scheduling or provider execution;
- automatic task owner persistence;
- heartbeat loops;
- lost-owner detection;
- provider socket freezing;
- automatic reattach;
- automatic approval forwarding;
- inactive-child execution;
- tool execution;
- storage writes from the helper;
- workspace mutation;
- hooks, automations, app-server listener, MCP runtime, swarm, memory, or learning runtime.
