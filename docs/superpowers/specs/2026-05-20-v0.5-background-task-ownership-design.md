# v0.5 Background Task Ownership And Reattach Design

日期：2026-05-20

## 1. Purpose

This design defines Tessera's first durable task ownership contract for background-capable work. It sits between the existing pause/resume envelope design and the future app-server / GUI live-provider path.

The goal is not to add a daemon yet. The goal is to make task ownership explicit, trace-backed, replayable, and safe to project from CLI, TUI, GUI, replay, and future runtime API clients.

## 2. Current Baseline

Already present:

- `TaskKind`, `TaskStatus`, `task_created`, `task_started`, `task_completed`, `task_failed`, `task_cancelled`, `task_paused`, and `task_resumed`.
- `RunControls`, `RunCancellationToken`, and `RunPauseToken` route control through core.
- `TaskPauseCheckpoint` records a provider-neutral resume envelope.
- `RuntimeReader::list_tasks` reconstructs task state from JSONL trace.
- `RuntimeReader::list_pause_checkpoints` reconstructs resumable pause checkpoints.
- CLI has chat-only `/resume-task <task_id|#>` and top-level `tessera tasks [--json]`.
- `RuntimeHttpApi` can shape read-only event pages as JSON/SSE frames, but no listener exists.
- GUI bridge is mock/replay and read-only; it does not own runtime execution.

Missing:

- No protocol type says which runtime instance owns active execution for a task.
- No heartbeat or lease metadata can distinguish "running and owned" from "stale running record".
- No trace-backed way for a new client to reattach as an observer.
- No clear lost-owner state for tasks whose process exited without a clean terminal event.
- No app-server design can safely expose background task control without this ownership layer.

## 3. Non-Goals

This slice must not implement:

- A long-lived daemon or listener process.
- Provider socket freezing.
- Provider-private execution handles.
- Tool execution.
- MCP runtime.
- Hook or automation runtime.
- Workspace restore/revert.
- File mutation or checkpoint restore.
- Sub-agent persistence.
- Swarm scheduling.
- Remote app-server access.

It also must not change the meaning of existing session resume or chat-only task resume. `/resume <trace_id|#>` remains trace projection. `/resume-task <task_id|#>` remains checkpoint-based chat resume.

## 4. Terminology

- **Execution owner:** the core runtime instance currently responsible for advancing a task.
- **Observer client:** a CLI/TUI/GUI/app-server client that is attached to task events but does not execute the task.
- **Ownership lease:** trace-backed metadata saying an owner claims responsibility for a task until a heartbeat expiry or terminal detach.
- **Heartbeat:** trace-safe evidence that the execution owner is still alive and has durably written up to a known sequence.
- **Lost owner:** a state derived or recorded when the latest execution lease expires without a terminal task event or clean detach.
- **Reattach:** a client reconnects to an existing owned task as an observer, or receives an honest result that the task is paused, terminal, or lost. Reattach does not mean the original provider socket can be revived.

## 5. Design Options

### Option A: Let Each Client Track Background Tasks In Memory

Each shell remembers the task IDs it started.

Pros:

- No protocol work.
- Simple for one CLI process.

Cons:

- Process exit loses state.
- GUI/TUI/app-server projections diverge.
- Replay cannot explain ownership.
- Automation and hooks would need their own state.

Rejected.

### Option B: Add A Daemon First

Start a persistent daemon and make all clients connect to it.

Pros:

- Natural home for background tasks.
- Useful for GUI/app-server later.

Cons:

- Too easy to create a second runtime before the trace contract is stable.
- Does not solve replay, stale-owner detection, or checkpoint semantics by itself.
- Adds auth/listener/process supervision before v0.5 has its ownership vocabulary.

Deferred.

### Option C: Trace-Backed Ownership Leases First

Core writes owner attach, heartbeat, detach, lost, and reattach metadata into trace. RuntimeReader reconstructs current ownership from JSONL. Future daemon/app-server implementations use the same events instead of inventing a new task store.

Pros:

- Fits Tessera's trace-first architecture.
- Provider-neutral and UI-neutral.
- Rebuildable from JSONL.
- Gives app-server and GUI a precise contract before a listener exists.
- Honest about lost processes and non-revivable provider streams.

Cons:

- Does not by itself keep tasks alive after process exit.
- Requires careful heartbeat semantics to avoid noisy traces.

Recommended.

## 6. Recommended Contract

Implement trace-backed ownership leases as the v0.5 contract.

The minimal lifecycle is:

```text
task_created
task_started
task_owner_attached(owner_kind=execution)
task_owner_heartbeat(last_seq=N, expires_at=...)
...
task_owner_detached(reason=completed|cancelled|failed|paused)
task_completed | task_cancelled | task_failed | task_paused
done
```

If a later observer sees a running task with an expired execution lease and no terminal task event, it may record:

```text
task_owner_lost(reason=heartbeat_expired)
```

If a client reconnects:

```text
task_reattach_recorded(mode=observe_existing_owner | resume_from_checkpoint | terminal_projection | owner_lost)
```

Reattach modes:

- `observe_existing_owner`: the execution owner is alive; the new client can read events from `since_seq` and send control intents through the owning runtime surface.
- `resume_from_checkpoint`: the task is paused and has a supported resume envelope.
- `terminal_projection`: the task is already completed, failed, or cancelled; the client receives replay/projection only.
- `owner_lost`: the owner lease expired; the client can show failure/lost-owner state or offer a future explicit recovery path.

## 7. Protocol Shape

Add IDs:

```rust
pub struct RuntimeInstanceId(String);
pub struct ClientInstanceId(String);
pub struct TaskOwnershipId(String);
```

Add metadata:

```rust
pub enum TaskOwnerKind {
    Execution,
    Observer,
}

pub enum TaskOwnerStatus {
    Attached,
    Heartbeat,
    Detached,
    Lost,
}

pub enum TaskReattachMode {
    ObserveExistingOwner,
    ResumeFromCheckpoint,
    TerminalProjection,
    OwnerLost,
}

pub struct RuntimeInstance {
    pub runtime_id: RuntimeInstanceId,
    pub process_id: Option<u32>,
    pub started_at: Timestamp,
    pub hostname: Option<String>,
    pub working_directory: Option<String>,
    pub capabilities: Vec<String>,
}

pub struct TaskOwnerLease {
    pub lease_id: TaskOwnershipId,
    pub task_id: TaskId,
    pub trace_id: String,
    pub runtime_id: RuntimeInstanceId,
    pub client_id: Option<ClientInstanceId>,
    pub owner_kind: TaskOwnerKind,
    pub status: TaskOwnerStatus,
    pub acquired_at: Timestamp,
    pub heartbeat_interval_ms: u64,
    pub expires_at: Option<Timestamp>,
    pub last_heartbeat_at: Option<Timestamp>,
    pub last_seq: Option<u64>,
    pub reason: Option<String>,
}

pub struct TaskOwnerHeartbeat {
    pub lease_id: TaskOwnershipId,
    pub task_id: TaskId,
    pub runtime_id: RuntimeInstanceId,
    pub heartbeat_at: Timestamp,
    pub expires_at: Timestamp,
    pub last_seq: u64,
}

pub struct TaskReattachRecord {
    pub task_id: TaskId,
    pub mode: TaskReattachMode,
    pub previous_lease_id: Option<TaskOwnershipId>,
    pub new_lease_id: Option<TaskOwnershipId>,
    pub checkpoint_id: Option<TaskPauseCheckpointId>,
    pub since_seq: Option<u64>,
    pub reason: Option<String>,
}
```

Add `RunEvent` variants:

- `RuntimeInstanceStarted { instance }`
- `TaskOwnerAttached { lease }`
- `TaskOwnerHeartbeat { heartbeat }`
- `TaskOwnerDetached { lease_id, task_id, reason }`
- `TaskOwnerLost { lease_id, task_id, reason }`
- `TaskReattachRecorded { record }`

All payloads must be metadata-only. They must not include API keys, headers, cookies, provider sockets, bearer tokens, process command lines containing secrets, full environment variables, tool output, or file contents.

## 8. Ownership Semantics

### Execution Owner

Only core can attach an execution owner. CLI, TUI, GUI, and app-server shells can request work, but they do not become execution owners by themselves.

An execution owner lease should be created when core commits to advancing a task. For the current no-tool chat and agent loops, this means after `task_started` and before provider request or agent run start.

An execution owner lease must detach when the task reaches a terminal or paused state.

### Observer Owner

Observer leases are optional metadata for clients that reconnect to a live task. They do not grant execution authority.

The first implementation can record reattach without adding observer leases if that keeps the slice smaller. The protocol should still distinguish owner kinds so GUI/app-server can grow into it.

### Heartbeat

Heartbeat is durable evidence, not a hidden in-memory timer.

Rules:

- Heartbeat interval must be explicit.
- Heartbeat payload stores the latest durable `seq` observed by the owner.
- Heartbeat expiry is advisory until a later observer records `task_owner_lost`.
- Heartbeat frequency should be coarse enough to avoid trace spam. A future default of 5-30 seconds is acceptable for long-running tasks; short one-shot runs may only write attach/detach.

### Lost Owner

A task is owner-lost when:

- latest task status is `Running` or `WaitingForApproval`;
- latest execution lease is `Attached` or `Heartbeat`;
- latest heartbeat `expires_at` is earlier than the observer's current time;
- no terminal, pause, or detach event supersedes it.

The first implementation can compute this state read-only. Recording `task_owner_lost` is useful when an active runtime/API surface performs recovery, but not required for passive replay.

## 9. RuntimeReader Projection

`RuntimeReader` should reconstruct ownership from trace:

- latest execution lease per task.
- latest observer lease per client/task if observer events exist.
- heartbeat expiry and last durable seq.
- whether reattach can observe live owner, resume from checkpoint, show terminal projection, or report owner lost.

Projection must remain rebuildable from JSONL. SQLite may index event kinds and task IDs, but must not become the ownership source of truth.

## 10. Client And UI Semantics

Client projection should eventually expose:

- `owner_status`: `owned`, `detached`, `lost`, or `none`.
- `owner_runtime_id`.
- `owner_last_seq`.
- `owner_expires_at`.
- `reattach_mode`.

User-facing wording should be honest:

- "Running" means task lifecycle says running.
- "Owned" means a runtime lease is current.
- "Lost" means Tessera cannot prove the original runtime still owns the task.
- "Reattach" means reconnect to events/control if the owner is alive, or resume from a checkpoint if the task is paused and resumable.

## 11. App-Server Alignment

This design is the prerequisite for a real app-server listener.

App-server must:

- use the same ownership events;
- expose bounded event pages with `since_seq`;
- expose task snapshots derived from `RuntimeReader`;
- require auth/session/origin checks before accepting control messages;
- never own a separate scheduler or task database.

The first app-server implementation can be a thin local transport over core-owned runtime commands. It must not call providers directly.

## 12. Failure Modes

### Process Exit Without Detach

Trace contains a running task and an attached lease whose heartbeat expires. New clients report owner lost. No provider socket is assumed alive.

### Provider Stream Still Running

Only the owning runtime may continue consuming it. Observer clients read events through bounded streams. If the owner disappears, the stream is lost.

### Paused Task

Ownership detaches with reason `paused`. Resume uses `TaskPauseCheckpoint` and writes `task_resumed` / reattach metadata as a new run path.

### Waiting For Approval

The execution owner may be idle while waiting, but the lease remains active. Heartbeat still matters because approvals may arrive from a different client later.

### Terminal Task

Terminal events supersede ownership. Reattach is projection only.

## 13. Phased Implementation

### Phase 1: Protocol And Trace Metadata

- Add ownership IDs, metadata, and events.
- Add protocol contract tests proving metadata serializes without secrets.
- Update protocol and trace docs.

### Phase 2: RuntimeReader Ownership Projection

- Add `RuntimeTaskOwnerSummary`.
- Add read-only reconstruction from `task_owner_*` and task lifecycle events.
- Add tests for current owner, detached owner, terminal superseding, and expired heartbeat.

### Phase 3: Core Ownership Recorder

- Add a small core-owned recorder/helper that writes attach, heartbeat, detach, lost, and reattach metadata through `TraceStore`.
- Keep it generic; no daemon, no listener, no provider-private handles.

### Phase 4: Integrate No-Tool Runs

- Add owner attach/detach around no-tool chat and agent run paths.
- Add coarse heartbeat only for long-running/waiting states if needed.
- Ensure terminal, pause, cancel, and failure paths detach ownership.

### Phase 5: Client/CLI Read-Only Surfacing

- Project owner status into `ClientTask`.
- Add script-friendly read-only CLI output for owner/reattach state.
- Keep existing `tessera tasks` paused-checkpoint behavior stable unless a clearly named flag/subcommand is added.

## 14. Acceptance Criteria

- Ownership state can be reconstructed from trace without mutable side tables.
- A running task can distinguish live-owner, detached, terminal, paused, and owner-lost states.
- Reattach outcome is explicit and provider-neutral.
- No payload stores provider-private socket handles, headers, cookies, API keys, env secrets, tool output, file content, or workspace mutation state.
- CLI/TUI/GUI/app-server remain clients; core remains the only execution owner.
- No daemon or listener is introduced before app-server auth/bounded-queue/generated-schema design lands.

## 15. Open Questions

- Should the first implementation record observer leases, or only reattach result records?
- Should heartbeat expiry be recorded as `task_owner_lost` immediately by a later observer, or remain purely derived until an operator asks for recovery?
- Should `RuntimeInstance` include a sanitized executable name, or is `process_id` plus capability list enough for v0.5?
- Should app-server and CLI use the same `ClientInstanceId` source, or should app-server sessions have a separate ID family?
