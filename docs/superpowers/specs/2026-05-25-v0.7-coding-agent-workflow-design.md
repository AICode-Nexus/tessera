# v0.7 Coding-Agent Workflow Design

## Goal

Define the first v0.7 coding-agent workflow foundation: provider-neutral protocol, trace, projection, and core coordination contracts for patch proposals, diff evidence, test evidence, checkpoint requirements, reviewer gates, and worktree-first mutation boundaries. This design must not introduce file mutation, shell execution, apply-patch execution, checkpoint restore, Git mutation, GUI-owned runtime state, or provider-owned tooling.

## Context

Tessera v0.1-v0.6 now has the pieces that a coding workflow must reuse:

- a single headless `core` runtime shared by CLI, TUI, GUI, replay, and future runtime APIs;
- provider-neutral trace events and JSONL as the event truth;
- v0.3 policy, approval, sandbox, ordered result, and checkpoint planner foundations;
- v0.5 no-tool `AgentLoop`, opt-in project instructions, read-only skills, task ownership metadata, and runtime API DTOs;
- v0.6 structured handoff, reviewer gates, sub-agent session metadata, runtime ownership metadata, and transcript artifact lifecycle metadata.

The remaining v0.7 gap is an honest project coding-agent workflow. It must be reviewable and recoverable before it can mutate files. The first slice should therefore create the design and implementation plan for metadata-first contracts and coordinator validation.

## Approaches Considered

### Recommended: Protocol-first workflow foundation

Add provider-neutral workflow metadata before any executor:

- patch proposal and diff evidence records;
- mutation scope and worktree mode metadata;
- checkpoint precondition records;
- test plan and test result summaries with artifact references;
- reviewer-gate linkage for accepting or rejecting proposed changes;
- a non-executing `CodingWorkflowCoordinator` in `core` that validates the gate sequence and returns events.

This follows the v0.3-v0.6 pattern: shape, replay, and projection first; execution later.

### Alternative: Build CLI `apply-patch` immediately

This would be more visibly useful, but it risks hidden file writes before policy, checkpoint, reviewer, and rollback semantics are replayable. It also tempts CLI to own mutation logic, which would violate the single-runtime boundary.

### Alternative: Start with GUI/TUI diff surfaces

This improves UX, but without trace and core coordination the UI would become the source of truth for review state. Tessera needs diff/review as projected runtime objects, not view-local state.

## Design

The v0.7 foundation should introduce a coding workflow as a trace-backed state machine. The initial implementation slice should be metadata-only.

### Workflow Objects

The protocol should represent these provider-neutral objects:

- `CodingWorkflowId`: one coding workflow attached to a task or handoff.
- `WorkspaceMutationScope`: root path label, allowed relative globs, denied relative globs, mutation mode, and whether worktree isolation is required.
- `MutationMode`: `WorktreeFirst`, `ExplicitLocal`, or `ReadOnlyProposal`.
- `PatchProposal`: patch id, workflow id, task id, summary, touched paths, diff artifact refs, risk labels, required checkpoint id, and reviewer gate id.
- `PatchApplicationRecord`: patch id, checkpoint id, outcome, conflict paths, applied path summary, and artifact refs. In the first implementation this is metadata-only and must not apply patches.
- `TestPlanRecord`: workflow id, commands as policy-controlled proposals, affected scopes, and required artifacts.
- `TestRunRecord`: command label, exit status summary, duration, stdout/stderr artifact refs, diagnostics refs, and secret-redaction status. In the first implementation this is metadata-only and must not run commands.
- `ReviewBundle`: reviewer gate id, patch proposal ids, test evidence refs, checkpoint refs, handoff refs, and summary text.
- `RestorePlanRecord`: checkpoint id, target paths, expected rollback mode, and reason. Restore execution remains blocked until workspace restore semantics exist.

The initial event set should be small and composable:

- `coding_workflow_started`
- `workspace_mutation_scope_recorded`
- `patch_proposal_recorded`
- `patch_application_recorded`
- `test_plan_recorded`
- `test_run_recorded`
- `review_bundle_recorded`
- `restore_plan_recorded`

Reviewer acceptance should use the existing v0.6 reviewer gate events rather than inventing a second approval system.

### Core Coordinator

`core` should own a non-executing `CodingWorkflowCoordinator` that validates event construction:

- workflow records must reference a task id;
- mutation scope must be relative to the project workspace and reject absolute or parent-traversal path patterns;
- `WorktreeFirst` should be the default mutation mode for file-changing workflows;
- patch proposals must include at least one touched path and at least one diff artifact reference;
- patch proposals that claim mutation readiness must reference a checkpoint and reviewer gate;
- patch application records must reference an existing proposal id and checkpoint id;
- test run records must use artifact references for command output rather than embedding raw output;
- restore plans must remain plan metadata and cannot trigger restore.

The coordinator should return `RunEvent` values only. It must not write files, call shell commands, run tests, apply patches, create worktrees, restore checkpoints, stage Git changes, call providers, write storage directly, or drive UI.

### Data Flow

1. A future no-tool or tool-using agent creates a coding workflow under a task.
2. Core records the workspace mutation scope and worktree requirement.
3. The agent or future tool proposes a patch as metadata plus diff artifact refs.
4. Core records a checkpoint requirement and review bundle.
5. A reviewer gate accepts, rejects, or requests revision over the bounded bundle.
6. Later v0.7 slices may execute patch application and test commands through policy/sandbox/checkpoint gates.
7. CLI/TUI/GUI/runtime API project the same trace-backed workflow state.

## Testing

The implementation plan should use TDD and keep the first slice metadata-only:

- protocol contract tests for serialization, event kind names, task ids, and secret-safe payload shape;
- core coordinator tests for validation and metadata-only event creation;
- client projection tests from live events and replayed trace records;
- GUI binding contract tests for generated DTOs and trace event kind coverage;
- docs and roadmap tests through `git diff --check`.

Final implementation verification remains:

```bash
PATH="$HOME/.cargo/bin:$PATH" cargo fmt --all -- --check
PATH="$HOME/.cargo/bin:$PATH" cargo clippy --workspace --all-targets -- -D warnings
PATH="$HOME/.cargo/bin:$PATH" cargo test --workspace
git diff --check
```

## Boundaries

This design does not permit:

- actual file mutation;
- apply-patch execution;
- shell, test, lint, or Git command execution;
- checkpoint restore/revert;
- YOLO mode;
- hidden patch application;
- GUI/TUI/CLI-owned mutation state;
- provider-owned tool execution;
- storage-owned runtime state machines;
- hooks, automations, MCP runtime, app-server listener, swarm, memory apply, or learning apply.

Future executable slices must pass through policy, sandbox, checkpoint, reviewer, trace, and worktree gates before mutating a workspace.
