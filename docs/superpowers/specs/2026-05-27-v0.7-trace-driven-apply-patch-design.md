# v0.7 Trace-Driven Apply-Patch Workflow Automation Design

## Goal

Design the next apply-patch slice after the explicit `tessera apply-patch` CLI envelope: a trace-driven mode that resolves an already-reviewed coding workflow bundle from trace records and then runs the same narrow core apply-patch gate and executor.

This is an ergonomics and replayability step, not a broader mutation runtime. It reduces duplicated CLI flags only when the trace already contains the required workflow, scope, mutation request, patch proposal, checkpoint, reviewer, policy, sandbox and patch artifact evidence.

## Current State

Tessera now has:

- provider-neutral coding workflow trace events for mutation scope, mutation request proposals, patch proposals, artifact body metadata, checkpoint lifecycle records, reviewer gates, policy decisions, apply-patch preflight records and apply-patch execution records;
- `TraceStore::read_trace_records` and artifact body storage for loading JSONL event metadata and out-of-band artifact bytes;
- `ApplyPatchGate`, which requires approved mutation metadata, checkpoint, reviewer, policy, sandbox, worktree-first scope, patch dry-run input and explicit executor context before `ExecutorReady`;
- `ApplyPatchExecutor`, which applies one UTF-8 create/modify patch inside a caller-supplied isolated root;
- an explicit `tessera apply-patch` command that builds a complete envelope from operator-supplied refs and appends preflight/execution metadata.

Tessera still does not have:

- trace lookup that turns prior workflow records into a complete apply envelope;
- stable disambiguation rules when a trace contains multiple workflows, mutation requests, patch proposals or patch artifacts;
- automatic isolated worktree lifecycle or cleanup;
- checkpoint creation or restore;
- test/lint runner integration;
- Git stage/commit/push/PR mutation;
- GUI/TUI/app-server mutation controls.

## Design Decision

Add a trace-driven mode to the existing apply-patch command rather than a second executor path.

The command should accept `--from-trace <trace_id>` and use a core-owned resolver over trace records to build a typed apply-patch envelope. The resolver must prove that the selected trace bundle is complete and accepted before the CLI calls the existing gate/executor path.

The trace remains metadata-only. Patch text is not read from `PatchProposalRecorded` or any other trace event payload. The patch body must come from exactly one safe source:

- a clean patch artifact body referenced by the selected patch proposal;
- an explicit `--patch-artifact-id <artifact_id>` that matches the selected patch proposal;
- an explicit local `--patch-file <path>` or `--stdin` override for manual recovery.

If no explicit patch source is provided, the resolver may auto-select a patch artifact only when the selected patch proposal has exactly one `diff_artifacts` entry with an artifact id, the matching `ArtifactBodyRecorded` metadata has `kind: patch`, non-zero byte length, a `tessera://artifacts/.../body` storage URI and `redaction_status: clean`, and `TraceStore::read_artifact_body` returns UTF-8 text within the existing patch byte limit.

## Command Shape

Recommended trace-driven mode:

```bash
tessera apply-patch \
  --from-trace trace_apply_patch_demo \
  --workflow-id coding_workflow_demo \
  --request-id mutation_request_demo \
  --patch-id patch_proposal_demo \
  --isolated-root /path/to/isolated/worktree \
  --root-label worktree:demo \
  --json
```

Optional disambiguators and overrides:

- `--workflow-id <id>`: required when the trace contains more than one coding workflow.
- `--request-id <id>`: required when more than one approved patch-application mutation request matches the selected workflow.
- `--patch-id <id>`: required when more than one patch proposal matches the selected request/workflow.
- `--patch-artifact-id <id>`: required when the selected patch proposal references more than one patch artifact.
- `--allowed-path <path>`: optional narrowing only. It may remove paths from the resolved allowed set but must not add paths outside the trace-backed scope/request/proposal intersection.
- `--preflight-id <id>` and `--execution-id <id>`: optional overrides. If omitted, the CLI can generate fresh ids before appending events.
- `--dry-run`: resolve the trace bundle and append preflight metadata only.

`--from-trace` is mutually exclusive with the explicit-envelope fields that fabricate acceptance from flags: `--checkpoint-id`, `--reviewer-gate-id`, `--policy-decision-id`, `--sandbox-profile`, `--trace-id`, and explicit `--workflow-id`/`--request-id`/`--patch-id` only remain as selectors, not proof of approval.

## Resolver Semantics

The resolver consumes sorted `TraceRecord` values and produces a typed envelope. It does not open files, read artifact bodies, append trace records, call providers, run tools or mutate the workspace.

Selection rules:

1. Select a `coding_workflow_started` event by `workflow_id`, or require `--workflow-id` if multiple workflows exist.
2. Select a `workspace_mutation_scope_recorded` event for the workflow and task. It must use worktree-first semantics, have `worktree_required: true`, and include safe relative `allowed_paths`.
3. Select a `mutation_request_proposal_recorded` event for the workflow/task. It must have `operation: patch_application`, `status: approved`, a required checkpoint id, reviewer gate id, policy decision id, sandbox profile label, `worktree_required: true`, and requested paths inside the selected scope.
4. Select a `patch_proposal_recorded` event for the same workflow/task. It must touch only paths allowed by the scope and requested by the mutation request. Its checkpoint and reviewer refs must match the mutation request when present.
5. Require a `snapshot_lifecycle_recorded` event for the required checkpoint id with `status: created`.
6. Require a `reviewer_gate_resolved` event for the selected reviewer gate id with `decision: accept`.
7. Require a `tool_policy_decision_recorded` event for the selected policy decision id with `outcome: allow`.
8. Resolve exactly one patch body source as described above.
9. Build an apply envelope whose evidence refs point back to the source trace range and selected artifact id.

Failure must be explicit and non-mutating. Ambiguous, missing, rejected, redacted, unsafe or inconsistent evidence should fail before any preflight is appended.

## Runtime Flow

Trace-driven apply should share the existing apply-patch execution path:

1. Resolve config and data directory.
2. Read `--from-trace` records from `TraceStore`.
3. Run `TraceApplyPatchResolver` over those records with selector options.
4. Load the selected patch body from artifact storage, patch file or stdin.
5. Build a `CliApplyPatchEnvelope` containing the trace-derived mutation request, patch proposal, mutation scope, checkpoint lifecycle, reviewer decision, policy decision, sandbox label, patch body and caller-supplied isolated root context.
6. Run `ApplyPatchGate`.
7. Append `RunEvent::ApplyPatchPreflightRecorded` to the same trace.
8. If `--dry-run`, stop after a successful `DryRunReady` preflight.
9. If applying, require `ExecutorReady`, call `ApplyPatchExecutor::apply_to_isolated_root`, then append `RunEvent::ApplyPatchExecutionRecorded`.
10. Print text or JSON output with selected IDs, affected paths, blocker labels, patch artifact id and trace id.

No new protocol event is required for this slice. The proof of execution remains `apply_patch_execution_recorded`, and the proof of prior approval remains the existing trace events it references.

## Trace Behavior

`--from-trace` is both the lookup trace and the append trace for the first slice. The command must not copy approval metadata into a separate trace unless a future design defines cross-trace evidence references and replay semantics.

The appended preflight/execution records should include bounded evidence refs to the source event range and patch artifact id where possible. They must not include:

- patch body text;
- old or new file contents;
- absolute isolated root paths;
- raw filesystem handles;
- stdout/stderr bodies;
- provider-private responses;
- hidden reasoning;
- API keys, cookies, authorization headers or other secrets.

## Safety Boundaries

Allowed:

- read existing trace records;
- read one clean patch artifact body through `TraceStore::read_artifact_body`, or one explicit patch source;
- use trace metadata to avoid repeated CLI refs;
- append preflight and execution metadata to the same trace;
- apply one UTF-8 create/modify patch inside a caller-supplied non-primary isolated root through the existing core executor.

Not allowed:

- infer approval from a patch summary, UI state, hidden model text or unlinked artifact;
- create, clean up, switch or delete worktrees;
- write the primary checkout;
- create or restore checkpoints;
- run shell commands, `git apply`, system `patch`, tests, linters or formatters;
- stage, commit, push or open PRs;
- execute provider tools or MCP tools;
- expose GUI/TUI/app-server mutation buttons;
- support multi-file, delete, rename, binary, mode-only or symlink target patches.

## Alternatives Considered

### Keep Explicit CLI Only

Rejected as the next v0.7 step. The explicit CLI is safe but too verbose for repeated workflow execution because it asks the operator to restate metadata that already exists in trace.

### Auto-Create Worktree During Trace Resolution

Rejected. Worktree lifecycle needs ownership, cleanup, failure retention, checkpoint semantics and trace references. Trace-driven apply still receives an existing isolated root from the caller.

### Read Patch Body From Trace Payload

Rejected. Trace events must remain replayable metadata and must not store patch bodies or file contents. Artifact body storage is the correct out-of-band body mechanism.

### GUI Apply Button First

Rejected. GUI/TUI/app-server surfaces must remain views or typed intent sources until shared runtime command semantics are stable. Trace-driven CLI keeps the contract auditable first.
