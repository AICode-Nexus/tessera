# v0.5 Single Agent Loop Design

日期：2026-05-19

## 1. Purpose

This design defines Tessera's first real single-agent runtime foundation. It turns the existing v0.5 agent metadata into a trace-backed runtime path without adding tools, hooks, automations, subagents, workspace mutation, or background process reattach.

The goal is deliberately narrow: an agent can run one bounded provider-neutral loop, produce a machine-readable summary, write trace events, obey cancellation/pause/no-progress controls, and be replayed without relying on CLI/TUI/GUI state.

## 2. Current Baseline

Already present:

- `TaskKind::AgentRun` exists in `tessera-protocol`.
- `AgentProfile` and read-only `AgentRegistry` exist.
- `ConversationEngine` owns provider/storage coordination for chat runs.
- `RunControls`, `RunCancellationToken`, and `RunPauseToken` already work for chat.
- `NoProgressDetector` exists and records provider-neutral no-progress signals.
- JSONL trace is the event truth; `RuntimeReader` and `ClientSnapshot` project task state from trace.
- CLI can run one-shot/interactive chat and trace-backed paused chat resume.

Missing:

- No `AgentLoop` / `AgentEngine` exists.
- No agent run envelope or run summary exists.
- No agent step lifecycle events exist.
- No CLI entrypoint can start an agent task.
- No replay projection exposes an agent run summary beyond generic task status.

## 3. Non-Goals

This slice must not implement:

- Tool execution.
- Shell/file/git/http/apply-patch tools.
- Project instruction file ingestion.
- Skill runtime activation.
- Hook runtime.
- Automation runtime.
- MCP runtime.
- Subagent persistence or fan-out.
- Workspace restore/revert.
- Provider socket freezing.
- GUI live-provider execution.

Any design that needs those features belongs to a later v0.5/v0.6/v0.7 slice.

## 4. Approaches Considered

### Approach A: Wrap `ConversationEngine` Directly

Add a CLI command that calls existing chat code and labels it as an agent externally.

Pros:

- Fastest implementation.
- Smallest code change.

Cons:

- Trace still says `TaskKind::Chat`.
- No agent run envelope or step lifecycle.
- Later skills/subagents would have to retrofit runtime semantics.

This is too shallow for v0.5.

### Approach B: Add A Narrow `AgentLoop` That Reuses Provider/Storage Patterns

Create `AgentRunRequest`, `AgentRunOutcome`, and `AgentLoop<P>`. It uses the same provider trait, `RunControls`, trace store, contextual append pattern, and no-progress detector as chat, but records `TaskKind::AgentRun` and agent-specific step/summary events.

Pros:

- Preserves single headless runtime.
- Creates the missing agent runtime seam without tools.
- Keeps CLI/TUI/GUI as clients over trace/projection.
- Gives later skills/instructions/background/subagents a real attachment point.

Cons:

- Some `ConversationEngine` helpers need extraction or duplication avoidance.
- Adds protocol surface that must stay conservative.

This is the recommended path.

### Approach C: Build A Full Agent Runtime With Skills And Instructions Now

Define instructions, skill activation, context loading, background ownership, and CLI UX together.

Pros:

- Closer to final coding-agent UX.

Cons:

- Violates current gates.
- Too many subsystems at once.
- Makes review and replay harder.

This should wait until the single-agent loop trace contract is stable.

## 5. Recommended Design

Implement Approach B.

The first `AgentLoop` is a bounded no-tool provider loop:

```text
AgentRunRequest
  -> AgentLoop creates TaskKind::AgentRun
  -> emits agent_run_started
  -> for each allowed step:
       emits agent_step_started
       calls provider through ChatProvider
       streams normal provider-neutral RunEvent values
       observes output with NoProgressDetector
       emits agent_step_completed
  -> emits agent_run_completed + task_completed + done
  -> returns AgentRunOutcome
```

For v1, the loop normally runs one provider step. `max_steps` still matters because it is part of the contract: `0` is rejected, `1` is the default, and future tool observations can extend the loop without changing the envelope.

## 6. Protocol Additions

Add conservative protocol types:

- `AgentRunSummary`
  - `task_id`
  - `profile_id`
  - `status`
  - `steps_completed`
  - `final_text`
  - `stop_reason`
  - `evidence_event_range`

- `AgentStepStatus`
  - `running`
  - `completed`
  - `failed`
  - `cancelled`
  - `paused`
  - `stopped_no_progress`

- `AgentStepSummary`
  - `task_id`
  - `step_index`
  - `status`
  - `assistant_text`
  - `stop_reason`

Add `RunEvent` variants:

- `AgentRunStarted { task_id, profile_id, objective }`
- `AgentStepStarted { task_id, step_index }`
- `AgentStepCompleted { summary }`
- `AgentRunCompleted { summary }`

The `objective` is user-provided input and may enter trace like `UserMessageRecorded` already does. Future slices can replace or supplement it with context handles and instruction-source references.

Do not add raw provider responses, hidden reasoning, instruction file contents, skill script output, or tool results in this slice.

## 7. Core Additions

Add:

- `AgentRunRequest`
- `AgentRunOutcome`
- `AgentLoop<P>`

The request should include:

- `trace_id`
- `provider_id`
- `profile_id`
- `agent_profile`
- `model`
- `objective`
- `context_references`
- `max_steps`
- `history`

The outcome should include:

- `trace_id`
- `task_id`
- `status`
- `summary`
- `assistant_text`
- `store`

`AgentLoop` should reuse the existing architectural pattern from `ConversationEngine`:

- core creates task/thread/turn/item ids.
- provider emits provider-neutral `RunEvent`.
- core wraps events in `EventFrame`.
- storage appends JSONL and updates SQLite through `TraceStore`.
- event sink receives frames after durable append.
- cancellation/pause/no-progress finish paths always write trace.

The first implementation may duplicate a small amount of `ConversationEngine` logic if extraction would create a risky refactor. If duplication grows, extract a shared private run context helper inside `core`.

## 8. Finish Semantics

### Completed

On normal completion:

```text
agent_step_completed(status=completed)
agent_run_completed(status=completed)
task_completed
done
```

### Cancelled

If `RunCancellationToken` or event sink cancellation fires:

```text
agent_step_completed(status=cancelled)
task_cancelled
done
```

The outcome status is cancelled and includes the reason.

### Paused

If `RunPauseToken` fires:

```text
agent_step_completed(status=paused)
task_pause_checkpoint_created
task_paused
done
```

This does not implement provider socket freezing or true background reattach. The checkpoint uses the current trace projection model, as chat pause does today.

### No Progress

If no-progress detection fires:

```text
no_progress_loop_detected
agent_step_completed(status=stopped_no_progress)
task_cancelled or task_failed
done
```

For consistency with current chat behavior, the first implementation should use `task_cancelled` with a `no progress: ...` reason. A later policy change can introduce a distinct stopped status if needed.

### Provider Failure

If provider capability or stream fails:

```text
error
agent_step_completed(status=failed)
task_failed
done
```

The raw provider response is not written to trace.

## 9. CLI Surface

Add a small script-friendly entrypoint:

```bash
tessera agent run --provider <profile_id> --goal "..."
tessera agent run --provider <profile_id> --goal "..." --json
```

For source-tree development:

```bash
PATH="$HOME/.cargo/bin:$PATH" cargo run -p tessera-cli -- agent run --provider mock --goal "summarize the current task" --json
```

Text output should show:

- trace id
- task id
- status
- short summary

JSON output should include:

- `trace_id`
- `task_id`
- `status`
- `steps_completed`
- `summary`
- `assistant_text`

Do not add interactive agent mode yet. The interactive REPL can call the agent loop in a later slice after non-interactive behavior is stable.

## 10. Client And Runtime Projection

The existing task projection should already show `TaskKind::AgentRun` as a task. Add projection only if new `agent_*` events need summary fields in `ClientSnapshot`.

The minimum required projection:

- task status updates from existing `task_*` events.
- agent run summary available from trace/replay output or CLI JSON.

Avoid making TUI/GUI understand agent internals in this slice. They should continue to render task status and normal messages from provider events.

## 11. Tests

Required contract tests:

- Protocol serializes agent run events and maps their `kind()` values.
- Core agent loop writes `task_created(kind=agent_run)`, `agent_run_started`, `agent_step_started`, provider events, `agent_step_completed`, `agent_run_completed`, `task_completed`, and `done`.
- Core agent loop cancellation writes agent step cancellation and `task_cancelled`.
- Core agent loop pause writes agent step paused, checkpoint, `task_paused`, and `done`.
- Core agent loop provider failure writes `error`, agent step failed, and `task_failed`.
- CLI `agent run --provider mock --goal ... --json` emits machine-readable trace/task/status/summary fields.
- CLI rejects `agent run --json` without a goal.

Optional in this slice:

- Client projection test for agent summary if a new client field is added.

## 13. Open Questions

- Should no-progress terminal state remain `task_cancelled` forever, or become a future `TaskStatus::Stopped`?
  - Recommendation: keep current `task_cancelled` behavior for now.
- Should `AgentRunStarted` include full objective text?
  - Recommendation: yes for parity with `UserMessageRecorded`; later instruction/context sources should be references.
- Should CLI support `--file` / `--stdin` for agent goals in the first slice?
  - Recommendation: no. Start with `--goal`, then add prompt sources once the command shape settles.
