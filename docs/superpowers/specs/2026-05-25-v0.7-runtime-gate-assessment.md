# v0.7 Runtime Gate Assessment

## Goal

Assess whether Tessera can safely move from the v0.7 metadata-only coding workflow foundation into executable apply-patch, test, checkpoint restore, worktree, and Git mutation workflows.

## Conclusion

Do not start executable apply-patch, shell/test execution, checkpoint restore, worktree mutation, Git mutation, hooks, automations, swarm, or learning apply yet. The v0.7 metadata foundation is complete, but the runtime gates that would make workspace mutation safe are still mostly foundation-level contracts rather than executable enforcement.

The next safe step is a dedicated runtime-gate closure plan. It should design and implement missing enforcement pieces in small slices before any workspace mutation path is connected to CLI, TUI, GUI, runtime API, providers, or agents.

## Current Foundation Evidence

Tessera already has several foundations required by a future coding-agent workflow:

- Provider-neutral coding workflow events and DTOs for workflow start, mutation scope, patch proposals, patch application records, test plans/runs, review bundles, and restore plans.
- A non-executing `CodingWorkflowCoordinator` that validates relative paths, diff evidence, test output artifact refs, checkpoint refs, reviewer gates, and restore-plan blocking while returning `RunEvent` values only.
- Read-only client and GUI binding projection from live events and replayed trace records.
- Tool descriptor, policy decision, approval, sandbox profile, workspace checkpoint, task ownership, reviewer gate, and trace foundations from v0.3-v0.6.

These are necessary but not sufficient for executable mutation.

## Gate Status

| Gate | Current Status | Missing Before Execution |
| --- | --- | --- |
| Policy | Foundation exists: tool descriptors, `PolicyGate`, approval projection, reviewer gates. | Policy must bind concrete apply/test/restore/Git commands to workflow IDs, mutation scope, checkpoint requirements, reviewer gates, and user approvals. |
| Sandbox | Foundation exists: workspace guardrail and OS sandbox profile metadata. | A real enforced executor boundary is missing; no command or patch operation should run until sandbox selection is applied rather than only recorded. |
| Checkpoint | Foundation exists: checkpoint metadata and snapshot trace events. | Real checkpoint creation, validation, retention, restore planning, restore execution policy, and failure recovery semantics are missing. |
| Worktree | Metadata exists through `MutationMode::WorktreeFirst` and `WorkspaceMutationScope`. | Worktree lifecycle creation, cleanup, path mapping, conflict handling, and trace ownership are missing. |
| Artifact Evidence | Handles and evidence refs exist. | Diff/test output artifact body storage, redaction, retention, and preview contracts must be explicit before UI or reviewers rely on them. |
| Single-Agent Loop | No-tool agent loop exists. | Tool-using coding-agent loop is not implemented; providers must not directly execute tools or mutate files. |
| Task Ownership | Owner metadata, heartbeat/lost/reattach records exist. | Durable runtime ownership transfer and app-server/listener ownership are still gated. |
| Reviewer Gate | Structured reviewer gate metadata exists. | Patch application must be mechanically blocked until accepted reviewer decisions and required checkpoints are present. |
| CLI/TUI/GUI | Shared client projection exists. | Mutation intents, diff preview, approval UX, artifact inspection, and failure states are not implemented. |
| Runtime API/App Server | DTO and bounded buffer foundations exist. | Listener/control plane is not live; mutation requests must not route through an app-server until auth, ownership, and policy gates are executable. |

## Allowed Next Slices

The following slices are safe because they still avoid workspace mutation:

1. Runtime gate closure design: define the minimum enforcement sequence for policy, sandbox, checkpoint, worktree, artifact, reviewer, and client-intent gates.
2. Protocol/client intent design for mutation requests as proposals only, without execution.
3. Artifact body and redaction design for patch diffs and test output summaries, without command execution.
4. Checkpoint lifecycle design for real snapshots and restore semantics, without implementing restore execution.
5. Worktree lifecycle design for isolated mutation contexts, without applying patches.

## Blocked Slices

The following remain blocked until the missing gates above are implemented and verified:

- apply-patch execution;
- shell, test, lint, or Git command execution;
- checkpoint restore/revert execution;
- GUI/TUI diff apply or Git mutation controls;
- hook runtime;
- automation runtime;
- app-server mutation listener;
- persistent child-agent execution that can mutate code;
- swarm execution over mutable workspaces;
- learning apply path.

## Recommended Next Plan

Create and execute a v0.7 runtime gate closure plan before any mutation runtime. The plan should start with documentation and protocol/client-intent contracts, then add enforcement primitives, and only after those pass should it add a narrow apply-patch executor.

The first executable mutation milestone should require all of the following to be true in tests:

- a workflow has a bounded mutation scope;
- a real checkpoint was created before mutation;
- sandbox/worktree enforcement is selected and trace-backed;
- patch diff artifact body is redacted and reviewable;
- reviewer gate decision is accepted;
- policy explicitly allows the requested operation;
- mutation result writes trace events and recoverable evidence;
- failure and restore-plan records are projected to CLI/TUI/GUI without UI owning runtime state.
