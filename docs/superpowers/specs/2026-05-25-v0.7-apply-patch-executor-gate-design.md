# v0.7 Apply-Patch Executor Gate Design

## Goal

Define the narrow gate between Tessera's v0.7 mutation metadata foundations and any future executable apply-patch runtime.

This design intentionally does not authorize file writes. It defines the next safe foundation slice: apply-patch preflight validation and dry-run projection over existing mutation request, checkpoint, policy, sandbox, reviewer and artifact records.

## Current State

Tessera can already represent coding-agent mutation intent without executing it:

- `MutationRequestProposal` records operation kind, requested paths, required checkpoint, reviewer gate, policy decision, sandbox profile and worktree requirement metadata.
- `PatchProposal`, `PatchApplicationRecord`, `TestPlanRecord`, `TestRunRecord`, `ReviewBundle` and `RestorePlanRecord` are provider-neutral trace metadata.
- `ArtifactBodyRecord` and `TraceStore` support artifact body handles and redaction metadata.
- `WorkspaceCheckpointLifecycleRecord` can record checkpoint lifecycle status, but restore remains blocked.
- `MutationEnforcementPlanner` defaults file-changing work to worktree-first, requires explicit policy for local mode, records sandbox metadata and rejects unsafe paths.

These foundations are still not an executor. No current crate should apply patches, run tests, create worktrees, restore checkpoints, mutate Git, call providers through tools, or drive mutation from CLI/TUI/GUI.

## Design Decision

The next safe slice is a non-mutating `ApplyPatchExecutionGate`, not an apply-patch executor.

The gate should answer one question: "Would this patch be eligible for a future executor if execution existed?" It should validate references and produce traceable readiness metadata, while keeping all workspace writes blocked.

This keeps the v0.7 progression honest:

1. Validate that an apply-patch request has all required approvals and evidence.
2. Parse and dry-run patch artifacts without touching files.
3. Project readiness and blockers to clients.
4. Only after that work is verified, create a separate executor plan for actual file writes.

## Preflight Inputs

The preflight helper should accept explicit records, not query storage internals or depend on UI state:

- workflow id and task id;
- mutation request proposal;
- patch proposal;
- diff artifact body record or artifact handle summary;
- workspace mutation scope;
- mutation enforcement plan;
- checkpoint lifecycle record;
- reviewer gate decision;
- policy decision metadata;
- optional restore plan metadata;
- operator label for audit only.

Storage remains responsible for event truth. The helper receives already loaded records and returns provider-neutral outcomes that callers can write as normal trace events.

## Required Checks

Preflight must reject readiness when any of these are missing or unsafe:

- mutation request status is not approved or does not match apply-patch semantics;
- requested paths and patch touched paths are outside the mutation scope;
- checkpoint lifecycle status is not `WorkspaceCheckpointLifecycleStatus::Created`;
- reviewer gate decision is missing or not `ReviewerDecisionKind::Accept`;
- policy decision is missing or does not allow the operation;
- sandbox profile label is missing or inconsistent with workspace writes;
- worktree-first mode is required but no isolated mutation root is recorded;
- diff artifact body is missing, unredacted when reviewable output is required, oversized, or not a supported patch media type;
- patch dry run detects path traversal, absolute paths, unsupported binary patches, ambiguous rename/delete behavior, or conflicts that require file reads not yet modeled.

## Dry-Run Scope

Dry run may parse patch metadata and produce a preview summary. It must not:

- open or write workspace files;
- create worktrees or directories;
- run `patch`, `git apply`, shell commands, tests, linters, formatters, or Git;
- store raw file contents in trace payloads;
- infer approval from UI state;
- mark a patch as applied.

Allowed dry-run outputs:

- normalized affected path list;
- operation summary such as create, modify, delete, rename unsupported, binary unsupported;
- conflict/blocker reasons;
- redaction and artifact reference summary;
- future executor readiness status.

## Trace And Projection

The first implementation should prefer existing event shapes where possible. If a new event is required, it must be metadata-only and provider-neutral, for example:

- `apply_patch_preflight_recorded`;
- `ApplyPatchPreflightRecord`;
- status values `blocked`, `dry_run_ready`, `executor_ready`.

If existing `MutationRequestProposal`, `PatchApplicationRecord` and `RestorePlanRecord` are enough, the implementation may avoid new protocol types and keep the new helper purely in `core` plus client summary projection.

The client and GUI projection should show readiness and blockers. They must not expose a "Run", "Apply", "Commit", or executable GUI action until an executor plan is separately approved.

## First Implementation Boundary

The next implementation plan should stop at:

- core preflight helper;
- patch artifact dry-run parser/summary;
- optional client/GUI read-only projection of preflight readiness;
- protocol and trace docs if a new event is introduced;
- roadmap updates that keep execution blocked.

It should not implement:

- actual file writes;
- checkpoint restore or revert;
- worktree creation or cleanup;
- test runner integration;
- shell command execution;
- Git stage/commit/push/PR;
- CLI/TUI/GUI mutation buttons;
- app-server mutation listener;
- provider-driven tool execution.

## Alternatives Considered

### Implement apply-patch immediately

Rejected. Tessera has metadata and enforcement planners, but not enough executable checkpoint, sandbox and worktree lifecycle behavior to safely mutate workspaces.

### Start with GUI diff controls

Rejected for this slice. GUI diff controls would be useful, but they should sit on top of a trace-backed preflight/dry-run record rather than inventing UI-owned mutation state.

### Start with test runner integration

Rejected. Test execution implies shell/process policy, sandbox launch and output artifact retention. Apply-patch preflight and dry-run are a smaller next gate.

## Acceptance Criteria

This gate is complete when:

- the spec and implementation plan exist in `docs/superpowers`;
- `docs/global-plan.md` names preflight/dry-run as the next conservative v0.7 slice;
- `docs/version-plan.md` clarifies that apply-patch execution remains gated after the design;
- no runtime code in this design commit applies patches or mutates files;
- `git diff --check` passes.
