# v0.7 Read-Only Diff/Review/Approval Inspection Design

## Goal

Make existing v0.7 coding workflow evidence easier to inspect from CLI, TUI
and GUI without adding execution controls or widening the trace surface.

## Scope

This slice is observation only. It may summarize patch proposals, review
bundles, reviewer gates, approvals, apply-patch preflights/executions and
artifact references already present in `ClientSnapshot` or trace records. It
must not load artifact bodies, render patch text, run tests, restore
checkpoints, stage/commit/push Git changes, execute shell/provider tools, start
an app-server listener, or add GUI/TUI mutation controls.

## Architecture

The implementation adds a small, UI-neutral inspection projection in
`tessera-client` built from the existing `ClientCodingWorkflow`,
`ClientReviewerGate` and `ClientApproval` data. This projection is safe by
construction: it contains generated ordinal display refs, status labels,
counts, boolean gates and artifact reference counts only. It deliberately
omits raw typed IDs, scope labels, free-form objective, summary, diagnostic,
comment, reason, touched path, requested path, target path and artifact-body
fields.

CLI inspection uses replayed `ClientSnapshot` state from trace records rather
than reading storage internals directly. TUI and GUI consume the same client
projection. GUI view-model helpers remain a second safety boundary by rendering
only the safe inspection row type.

## Safe Inspection Fields

For each workflow row:

- `workflow_ref`
- `task_ref`
- `active`
- `mutation_mode`
- `worktree_required`
- `patch_count`
- `diff_artifact_ref_count`
- `patches_requiring_review_count`
- `review_bundle_count`
- `review_evidence_ref_count`
- `reviewer_gate_count`
- `accepted_reviewer_gate_count`
- `rejected_reviewer_gate_count`
- `revision_requested_reviewer_gate_count`
- `pending_reviewer_gate_count`
- `approval_count`
- `pending_approval_count`
- `resolved_approval_count`
- `apply_patch_preflight_count`
- `executor_ready_preflight_count`
- `executor_blocked_preflight_count`
- `apply_patch_execution_count`
- `successful_apply_patch_execution_count`
- `failed_apply_patch_execution_count`

The projection may include status enum labels derived from typed records. It
must not include patch summaries, review summaries, diagnostics, comments,
reason text, raw ids, scope labels, paths, objective text, shell commands,
stdout/stderr bodies, patch bodies, artifact bodies or local filesystem
handles.

`workflow_ref` and `task_ref` are generated display labels such as
`workflow:1` and `task:1` assigned after deterministic sorting. They are not
derived from trace-provided id text. Raw typed ids are still used internally to
join workflow, review gate and approval records, but they must not leave the
inspection projection.

## CLI Surface

Add:

```bash
tessera workflow inspect --trace <trace_id> [--json]
```

Text output should be compact and path-free, for example:

```text
workflow workflow:1 task=task:1 active=true patches=1 diff_refs=1 review_bundles=1 reviewer_gates=1 accepted=1 pending=0 approvals=0 preflights=1 executor_ready=0 executions=0
```

JSON output should serialize only the safe projection rows. Empty traces should
print `workflow inspection records: none` in text mode and `[]` in JSON mode.

## TUI Surface

Extend the status line with a compact inspection summary derived from
`ClientStatus`, for example:

```text
inspection workflows 1 / review gates 1 accepted / approvals 0 pending / diff refs 1
```

The TUI remains a view. It does not add keybindings, commands, execution
handlers, provider calls or storage access.

## GUI Surface

Add a read-only `Review Inspection` panel beside the existing workflow/worktree
metadata panels. It renders safe row fields only, using stable row helpers in
`apps/gui-tauri/src/view-model.ts`. The panel must not render raw
`ClientCodingWorkflow`, `PatchProposal`, `ReviewBundle`, `ReviewerGate`,
`ClientApproval` or artifact body fields directly.

The GUI must continue to omit local paths, touched paths, requested paths,
workflow objective text, raw ids, scope labels, patch/review/test summaries,
diagnostics, reason text, reviewer comments, artifact bodies and mutation
controls.

## Documentation Updates

Update `docs/version-plan.md`, `docs/global-plan.md`,
`docs/coding-agent-direction.md`, `docs/protocol-v0.md`,
`docs/trace-schema-v0.md` and `CHANGELOG.md` after implementation lands. The
docs should mark read-only diff/review/approval inspection as implemented and
keep diff apply, test execution, checkpoint restore, GUI mutation controls,
Git mutation, app-server mutation listener, hooks, automations, swarm and
learning as future gated work.

## Verification

Required gates:

```bash
git diff --check
PATH="$HOME/.cargo/bin:$PATH" cargo fmt --all -- --check
PATH="$HOME/.cargo/bin:$PATH" cargo clippy --workspace --all-targets -- -D warnings
PATH="$HOME/.cargo/bin:$PATH" cargo test --workspace
cd apps/gui-tauri && npm test
cd apps/gui-tauri && npm run build
```

Focused tests must include negative fixtures containing path-like and
secret-like raw ids, root labels, allowed/denied paths, objective, summary,
diagnostic, reason, comment, touched path, requested path, restore target path,
restore reason, evidence label/summary, test command labels, stdout/stderr
artifact references, preflight/execution affected and conflict paths, executor
block reason text and artifact body text. Assert those strings do not appear in
CLI JSON/text output, TUI status output, GUI rows or rendered DOM.
