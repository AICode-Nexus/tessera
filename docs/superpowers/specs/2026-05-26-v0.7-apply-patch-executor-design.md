# v0.7 Apply-Patch Executor Design

## Goal

Define Tessera's first file-writing apply-patch executor contract without implementing the executor in this design slice.

The previous v0.7 apply-patch gate made preflight and dry-run readiness explicit while always returning `executor_blocked`. This design describes the next runtime-capable boundary: how a future executor may move from `executor_blocked` to `executor_ready`, what evidence it must require, what it may write, and what it must record.

This design authorizes a future implementation plan. It does not authorize immediate patch execution in the current runtime.

## Current State

Tessera now has the required metadata foundation for an executor plan:

- `MutationRequestProposal` records operation kind, requested paths, checkpoint, reviewer, policy, sandbox, and worktree requirements.
- `WorkspaceMutationScope` and `MutationEnforcementPlan` keep file-changing workflows worktree-first by default.
- `WorkspaceCheckpointLifecycleRecord` records checkpoint lifecycle status, but restore remains non-executable.
- `ReviewerGateDecision` and policy metadata can represent explicit approval.
- `ApplyPatchPreflightRecord` records preflight status, blockers, affected paths, dry-run operation summaries, and an explicit executor-blocked reason.
- `ApplyPatchGate` can parse bounded patch body text for dry-run summaries without touching the workspace.

The current code still must not apply patches, create worktrees, run tests, restore checkpoints, stage or commit Git changes, execute shell commands, or expose a CLI/TUI/GUI mutation button.

## Design Decision

The first apply-patch executor should be core-owned, worktree-first, in-process, and narrowly scoped to one UTF-8 text file create or modify operation.

Core owns orchestration and gate binding. The executor owns only patch document validation, in-memory application, and the final atomic write inside an explicitly supplied isolated mutation root. CLI, TUI, GUI, runtime API, and future app-server surfaces may request or project executor state, but they must not own execution or infer approval from view state.

The first executor implementation must:

1. Require an `ApplyPatchPreflightRecord` or equivalent gate output with `status: ExecutorReady` and `executor_blocked: false`.
2. Preserve today's default: ordinary dry-run-ready records remain blocked with `apply_patch_executor_not_implemented` or its future equivalent.
3. Require explicit mutation request approval, reviewer accept, policy allow, sandbox profile, checkpoint lifecycle proof, and worktree isolation proof.
4. Write only inside an explicitly supplied isolated mutation root.
5. Reject any root label that represents the primary project root, local root, or unknown workspace authority.
6. Reject absolute paths, parent traversal, symlinked target paths or parent directories, unsupported binary/delete/rename patches, and multi-file patches until transaction semantics exist.
7. Apply no shell, no `patch`, no `git apply`, no Git mutation, no formatter/test command, and no provider tool call.
8. Record trace metadata for intent, result, blockers, artifact refs, checkpoint refs, and affected paths without embedding patch bodies or file contents.

## Execution Boundary

### Allowed In First Runtime Slice

- Parse one patch artifact body that has already passed artifact body/redaction checks.
- Support one UTF-8 text file create or modify patch.
- Validate the target path lexically and against the isolated root.
- Reject symlinked ancestors and symlinked target files before writing.
- Read the target file only for modify operations.
- Compute the post-patch contents in memory.
- Write through a temp file in the same directory and rename on success.
- Return a structured execution record for success, conflict, rejection, or internal failure.

### Not Allowed In First Runtime Slice

- Creating, deleting, cleaning, or switching worktrees.
- Writing the primary project root or an unlabelled local root.
- Multi-file patches.
- Rename, delete, chmod, binary, submodule, or mode-only patches.
- Running shell commands, external patch tools, tests, linters, formatters, or Git.
- Checkpoint restore or workspace revert.
- GUI/TUI/CLI apply buttons that bypass core-owned executor intent.
- App-server mutation listeners.
- Provider-owned tool execution.

## Required Inputs

The executor request should be explicit and replay-auditable. It should receive already resolved records or stable references; it must not query UI state or storage internals to discover permission.

Required input categories:

- workflow id and task id;
- mutation request id and approved mutation request summary;
- patch proposal id and artifact body handle;
- apply-patch preflight id with executor-ready status;
- workspace mutation scope;
- mutation enforcement plan with isolated worktree requirement;
- isolated mutation root descriptor with a non-primary root label;
- checkpoint lifecycle id with created status;
- reviewer gate decision id with accept status;
- policy decision id with allow status;
- sandbox profile label;
- redaction/artifact refs for traceable evidence;
- operator or request source label for audit metadata.

The isolated root descriptor must be supplied by a future worktree/checkpoint owner. The first apply-patch executor must not create the worktree itself.

## Path And Filesystem Safety

The executor must treat patch paths as untrusted input even after dry-run.

It must reject:

- absolute paths;
- empty paths;
- `.` or `..` components;
- paths containing parent traversal after normalization;
- platform-specific drive prefixes;
- paths outside `WorkspaceMutationScope.allowed_paths`;
- paths that resolve outside the isolated mutation root;
- symlinked parent directories;
- symlinked target files;
- target directories for file writes;
- non-UTF-8 target paths;
- unsupported patch operations.

For modify operations, the executor should read the current file, verify hunk context, and classify mismatches as conflicts rather than partial success. For create operations, it should reject existing targets unless the patch explicitly models modify semantics.

## Atomicity And Failure Semantics

The first executor avoids partial-workspace ambiguity by supporting only one file.

Execution should follow this order:

1. Validate all gate records and path constraints.
2. Parse the patch document and confirm exactly one supported operation.
3. Read current file contents when needed.
4. Compute the new contents in memory.
5. Write a temp file in the target directory.
6. Rename the temp file over the target only after all validation passes.
7. Remove the temp file on recoverable failure when possible.
8. Emit an execution result that never claims success if any validation, hunk, write, or rename step failed.

If multi-file support is added later, it must first define transaction, rollback, and checkpoint restore semantics. Until then, multi-file patches are rejected.

## Trace And Protocol

The implementation plan should add a first-class execution record rather than overloading the existing metadata-only `PatchApplicationRecord`.

Recommended new protocol shape:

- `ApplyPatchExecutionId`;
- `ApplyPatchExecutionRecord`;
- `ApplyPatchExecutionStatus` with values such as `planned`, `applied`, `conflict`, `rejected`, `failed`;
- `ApplyPatchExecutionBlocker`;
- `RunEvent::ApplyPatchExecutionRecorded`.

The execution record should include:

- execution id;
- preflight id;
- workflow id and task id;
- mutation request id;
- patch proposal id;
- checkpoint lifecycle id;
- reviewer/policy/sandbox refs;
- isolated root label, not an absolute filesystem handle;
- executor label/version;
- status;
- affected path summary;
- blocker labels;
- conflict path summary;
- artifact refs for diff/result evidence;
- timing metadata if already available in the caller.

It must not include:

- patch body text;
- file contents;
- stdout/stderr bodies;
- provider-private responses;
- hidden reasoning;
- API keys, cookies, authorization headers;
- raw filesystem handles or primary-root paths.

`PatchApplicationRecord` may remain as a user-facing summary/projection if needed, but docs must keep it distinct from the runtime execution event.

## Client And UI Boundary

Client, TUI, GUI, and future app-server surfaces remain consumers or explicit intent sources. They may show:

- preflight readiness;
- execution status;
- affected paths;
- blockers/conflicts;
- evidence artifact refs;
- checkpoint/reviewer/policy links.

They must not:

- apply patches directly;
- infer approval from a visible button state;
- expose Git mutation before the patch/checkpoint gate closes;
- hide conflicts or partial failure;
- claim a patch was applied unless a core-owned execution event says so.

Any future apply button must create an explicit runtime intent and be trace-backed. It must still be rejected unless the core executor gates are satisfied.

## Alternatives Considered

### Reuse `PatchApplicationRecord` As The Executor Event

Rejected for the first implementation. `PatchApplicationRecord` already exists as metadata-only workflow foundation. Overloading it would blur the difference between "planned/applied metadata" and a runtime write. A first-class execution record keeps trace semantics honest.

### Use `git apply` Or System `patch`

Rejected. External commands would immediately require shell/process policy, sandbox launch, command output artifact retention, and Git/worktree error handling. An in-process single-file executor is smaller and more auditable.

### Implement Multi-File Patch Support First

Rejected. Multi-file support needs transaction and rollback semantics. A single-file first slice can prove path safety, hunk conflict handling, artifact refs, and execution trace shape without pretending checkpoint restore already exists.

### Let GUI Own Patch Application

Rejected. GUI remains a view/client. Runtime execution must stay in the shared headless runtime so CLI, TUI, replay, GUI, and future runtime APIs share one contract.

## Acceptance Criteria For This Design Slice

This design slice is complete when:

- this spec exists under `docs/superpowers/specs`;
- an implementation plan exists under `docs/superpowers/plans`;
- `docs/global-plan.md` names executable apply-patch executor design as the next v0.7 step while keeping runtime writes unimplemented;
- `docs/version-plan.md` clarifies the first executor boundary and remaining gates;
- `CHANGELOG.md` records the design;
- no runtime code is added in this commit;
- `git diff --check` passes.
