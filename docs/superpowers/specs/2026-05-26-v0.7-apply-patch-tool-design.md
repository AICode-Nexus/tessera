# v0.7 Apply-Patch Tool Design

## Goal

Define the first user-facing apply-patch tool over Tessera's narrow core executor without expanding into worktree creation, test execution, checkpoint restore, Git mutation, GUI mutation controls, or provider-owned tool execution.

The previous slice added a core-owned, in-process, isolated-root, single-file UTF-8 create/modify executor. This design describes the next safe surface: a CLI command that lets an operator run that executor only through explicit gate inputs and trace-backed result metadata.

## Current State

Tessera now has:

- `ApplyPatchGate`, which can produce `ExecutorReady` only when mutation request, reviewer, policy, checkpoint, sandbox, worktree scope, patch dry-run, and explicit executor context checks pass.
- `ApplyPatchExecutor`, which applies one UTF-8 create/modify patch inside a caller-supplied isolated root and returns `ApplyPatchExecutionRecord`.
- Protocol events for `ApplyPatchPreflightRecorded` and `ApplyPatchExecutionRecorded`.
- Read-only client and GUI bindings that project execution records.

Tessera still does not have:

- a user-facing apply-patch CLI command;
- trace lookup that reconstructs a complete apply request from prior workflow records;
- automatic isolated worktree creation or cleanup;
- checkpoint creation or restore;
- test runner integration;
- Git stage/commit/push/PR mutation;
- GUI/TUI apply buttons.

## Design Decision

Add a conservative top-level CLI command named `tessera apply-patch`.

The command is an explicit apply envelope. It does not discover permission from UI state, hidden model output, or partial trace projection. The operator must provide all gate refs and an isolated root descriptor on the command line. The command reads patch body text from exactly one local source, runs the existing core gate, records preflight metadata, and only calls the executor when the gate returns `ExecutorReady`.

This first command is intentionally verbose. A future trace-driven command can reduce flags by loading a reviewed workflow bundle from trace, but that requires stable trace lookup semantics and is out of this slice.

## Command Shape

Recommended first CLI shape:

```bash
tessera apply-patch \
  --trace-id trace_apply_patch_demo \
  --workflow-id coding_workflow_demo \
  --task-id task_demo \
  --request-id mutation_request_demo \
  --patch-id patch_proposal_demo \
  --preflight-id apply_patch_preflight_demo \
  --execution-id apply_patch_execution_demo \
  --checkpoint-id snapshot_before_apply \
  --reviewer-gate-id reviewer_gate_apply \
  --policy-decision-id policy_apply \
  --sandbox-profile workspace_write_isolated \
  --isolated-root /path/to/isolated/worktree \
  --root-label worktree:demo \
  --allowed-path docs/README.md \
  --patch-file /path/to/patch.diff \
  --data-dir /tmp/tessera-data \
  --json
```

Patch body source must be exactly one of:

- `--patch-file <path>`;
- `--stdin`.

The command must reject:

- missing isolated root;
- `--root-label project`, `--root-label local`, or an empty root label;
- no `--allowed-path`;
- absolute or parent-traversing allowed paths;
- more than one patch source;
- missing checkpoint, reviewer, policy, sandbox, workflow, task, request, patch, preflight, or execution refs;
- `--dry-run` combined with expectations that files changed.

## Dry-Run Mode

The command may support `--dry-run` in the first slice.

Dry-run still reads the patch body and runs `ApplyPatchGate`, but it does not provide executor context and never calls `ApplyPatchExecutor`. It records an `ApplyPatchPreflightRecorded` event and exits with success only when the gate reaches `PreflightReady`.

Dry-run output must say `executor_blocked: true` and must not claim that the patch was applied.

## Runtime Flow

For a real apply:

1. Resolve config and data directory through existing CLI helpers.
2. Read patch body from file or stdin into memory.
3. Build explicit provider-neutral records from CLI arguments:
   - `MutationRequestProposal` with `status: Approved`;
   - `PatchProposal`;
   - `WorkspaceMutationScope` using `mutation_mode: WorktreeFirst`;
   - `MutationEnforcementPlan`;
   - `WorkspaceCheckpointLifecycleRecord` with `status: Created`;
   - `ReviewerGateDecision` with `decision: Accept`;
   - `ToolPolicyDecision` with `outcome: Allow`;
   - `ApplyPatchExecutorContext` with `root_kind: IsolatedWorktree`.
4. Run `ApplyPatchGate`.
5. Convert the gate output into `ApplyPatchPreflightRecord`.
6. Append `RunEvent::ApplyPatchPreflightRecorded` to the selected trace.
7. If the gate is not `ExecutorReady`, print blockers and exit non-zero.
8. Call `ApplyPatchExecutor::apply_to_isolated_root`.
9. Append `RunEvent::ApplyPatchExecutionRecorded` to the same trace.
10. Print text or JSON summary.

The command appends only metadata events. It must not store patch bodies or file contents in trace.

## Trace Behavior

`--trace-id` should be optional. If omitted, the CLI can generate a trace id with an `apply_patch_` prefix and a monotonic timestamp. If supplied and the trace already exists, the command appends after the last sequence number.

The first slice should append:

- preflight event for all dry-run and apply attempts;
- execution event only when the executor was invoked.

It should not invent full chat, agent, or coding-workflow traces. Later trace-driven workflow work can add richer event bundles.

## Output

Text output should be scan-friendly:

```text
apply-patch preflight executor_ready affected=docs/README.md trace=trace_apply_patch_demo
apply-patch execution applied affected=docs/README.md trace=trace_apply_patch_demo
```

JSON output should include:

- trace id;
- preflight status;
- execution status when present;
- affected paths;
- conflict paths;
- blocker labels;
- executor label;
- isolated root label.

It must not include patch body, new file contents, old file contents, stdout/stderr bodies, cookies, API keys, authorization headers, or absolute target filesystem paths.

## Safety Boundaries

Allowed:

- one UTF-8 text file create/modify patch;
- explicit isolated root supplied by the caller;
- explicit allowed paths;
- appending trace metadata;
- writing one file through the core executor.

Not allowed:

- automatic worktree creation or cleanup;
- writing the primary checkout;
- shell commands, `git apply`, system `patch`, tests, linters, or formatters;
- checkpoint restore or workspace revert;
- Git stage/commit/push/PR;
- provider tool execution;
- GUI/TUI/app-server mutation controls;
- multi-file, delete, rename, binary, mode-only, or symlink target patches.

## Alternatives Considered

### Trace-Driven Apply First

Rejected for this slice. It would be more ergonomic, but Tessera does not yet have stable lookup semantics for resolving a complete approved mutation bundle from trace IDs. Building that first would expand the scope beyond a narrow apply tool.

### Auto-Create Worktree First

Rejected. Worktree lifecycle needs ownership, cleanup, failure retention, checkpoint semantics, and trace references. The current executor intentionally receives an existing isolated root from outside.

### GUI/TUI Apply Button First

Rejected. UI surfaces must remain views or explicit intent sources. A button before a CLI/core contract would make UI state too powerful and would weaken the shared runtime boundary.

### Use `git apply`

Rejected. External patch tools require shell/process policy, command output retention, sandbox launch semantics, and Git/worktree error handling. The existing in-process executor is smaller and easier to audit.

## Acceptance Criteria For This Design Slice

This design slice is complete when:

- this spec exists under `docs/superpowers/specs`;
- an implementation plan exists under `docs/superpowers/plans`;
- `docs/global-plan.md` names the user-facing apply-patch CLI tool as the next v0.7 step while keeping worktree lifecycle, test runner, checkpoint restore, Git, GUI/TUI mutation controls, hooks, automations, app-server mutation listener, swarm, and learning apply blocked;
- `docs/version-plan.md` clarifies that the first tool is explicit-envelope CLI only;
- `CHANGELOG.md` records the design;
- no runtime code is added in this commit;
- `git diff --check` passes.
