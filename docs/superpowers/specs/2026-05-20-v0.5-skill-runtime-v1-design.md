# v0.5 Skill Runtime v1 Design

Date: 2026-05-20

## 1. Purpose

This design defines Tessera's first skill runtime slice. It turns the existing read-only `SkillManifest` / `SkillRegistry` foundation into a bounded, traceable, provider-neutral way to discover `SKILL.md` files and explicitly activate selected skills for a no-tool `AgentLoop` run.

The goal is narrower than a plugin system:

- discover project-local `SKILL.md` entrypoints from explicit workspace scope.
- parse simple `SKILL.md` frontmatter into `SkillManifest` metadata.
- load redacted skill instruction text only after explicit activation.
- support read-only, explicitly requested reference files under the selected skill directory.
- record trace-safe activation and step metadata without persisting skill text.
- allow CLI inspection before any skill context is sent to a provider.

This slice must not execute shell commands, scripts, tools, MCP servers, hooks, automations, or file mutations. It must not import user-global skills by default.

## 2. External Direction

Modern coding-agent tools use skills as progressive disclosure: small top-level instructions point to deeper references and helper scripts. Tessera should adopt that shape without adopting unchecked execution.

The relevant product lessons are:

- `SKILL.md` should be the first compatibility target.
- Skill activation must be auditable, because a skill can change model behavior as much as an instruction file.
- Reference files should be loaded deliberately and boundedly, not recursively copied into prompts.
- Helper scripts can exist in skill directories, but v0.5 must treat them as inert metadata.
- CLI, TUI, GUI, replay and future app-server surfaces must all see the same trace-backed activation evidence.

## 3. Current Baseline

Already present:

- `SkillId`, `SkillSource`, `SkillEntrypoint`, `SkillRequirements`, `SkillPolicy` and `SkillManifest` in `tessera-protocol`.
- A read-only `SkillRegistry` in `tessera-core` with list/find behavior only.
- A no-tool `AgentLoop` with provider-neutral agent run/step events and machine-readable summaries.
- Opt-in project instruction discovery with byte limits, source reporting, redaction and `instructions_discovered` metadata.
- `tessera agent run` as the current non-interactive agent entrypoint.

Missing:

- No filesystem discovery for project-local `SKILL.md` files.
- No parser for `SKILL.md` frontmatter and body.
- No trace event records skill activation or skill context source metadata.
- No core-owned skill context renderer for `AgentLoop`.
- No CLI command can inspect discovered skills.
- No explicit `agent run --skill <id>` path.
- No read-only reference loading boundary for skill `references/` content.

## 4. Non-Goals

This slice must not implement:

- user-global skill discovery from `$HOME`, `$CODEX_HOME`, `$CLAUDE_HOME` or config directories by default.
- automatic skill activation from model text.
- shell/script execution from a skill directory.
- tool execution, file mutation, git mutation, HTTP fetch, apply-patch, MCP runtime, browser runtime or computer-use.
- hook runtime or automation runtime.
- sub-agent spawning or reviewer gate.
- skill install/update/delete commands.
- semantic skill ranking, embeddings, long-term memory, learning or auto routing.
- recursive import expansion for arbitrary paths.
- persistent background task ownership or provider socket reattach.

## 5. Approaches Considered

### Approach A: Discovery And Inspect Only

Add a core discovery planner and `tessera skills inspect`, but do not pass skill text into `AgentLoop`.

Pros:

- Very safe first step.
- Easy to test.
- No provider prompt behavior changes.

Cons:

- Does not validate activation trace semantics.
- Leaves the no-tool agent path unable to exercise skill-compatible context.

### Approach B: Explicit Activation With Read-Only Context

Add discovery/inspect, then allow `tessera agent run --skill <id> --workspace <path>` to explicitly activate one or more discovered skills. Core loads bounded, redacted `SKILL.md` bodies and any explicitly requested reference files, emits trace-safe activation metadata, and renders a stable-prefix skill context message.

Pros:

- Exercises the real runtime path without surprising defaults.
- Keeps CLI/TUI/GUI out of filesystem loading.
- Creates replayable evidence for later GUI/app-server surfaces.
- Provides a natural next step after project instruction discovery.

Cons:

- Adds CLI surface area.
- Requires careful ordering when project instructions and skills are both present.

### Approach C: Full Executable Skill Runtime

Allow skills to declare scripts/tools/hooks and execute them as part of the agent loop.

Pros:

- Closest to advanced coding-agent products.

Cons:

- Violates v0.5 tool/policy/sandbox gates.
- Would introduce unchecked execution before reviewer, checkpoint and background ownership contracts exist.
- Too much blast radius for this release stage.

Recommended path: Approach B. Keep activation explicit and read-only. Record enough metadata now so later v0.6/v0.7 work can add subagents, tools and policy-backed script execution without replacing the contracts.

## 6. Discovery Semantics

Inputs:

- `workspace_root`: explicit path, normally from `--workspace`.
- `target_dir`: explicit path or `workspace_root`.
- `skill_roots`: default to `workspace_root/.tessera/skills`; additional roots can be passed by tests or future config, but not loaded from user-global locations by default.
- `entrypoint_name`: initially `SKILL.md`.
- per-entrypoint byte limit: default `64 KiB`.
- per-reference byte limit: default `32 KiB`.
- combined loaded-byte limit: default `128 KiB`.
- placement: default `stable_prefix`.

Path rules:

- Canonicalize `workspace_root`.
- Canonicalize `target_dir` and require it to be inside `workspace_root`.
- Canonicalize each skill root and require it to be inside `workspace_root`.
- Missing skill roots produce an empty discovery report plus an optional warning; they are not fatal.
- Discover only immediate skill directories containing `SKILL.md` in configured skill roots.
- Do not follow symlinks for skill roots, skill directories, `SKILL.md` or references.
- Only regular UTF-8 files are loadable.
- Invalid candidates remain in the discovery report with warnings, but their content is not loaded.

Manifest parsing:

- The entrypoint should start with frontmatter delimited by `---`.
- v1 reads flat `name`, `description` and optional `version`.
- Unknown frontmatter keys are preserved only as safe metadata when scalar and small; executable keys such as `allowed-tools`, `hooks`, `scripts`, `commands` and `mcp` are ignored for runtime behavior.
- Skill id is derived from `name` by lowercasing and replacing non `[a-z0-9_-]` runs with `_`, then prefixing `skill_` if needed.
- Missing `name` or `description` makes the candidate invalid.
- Duplicate skill ids keep the first deterministic source and mark later candidates as skipped duplicate.

Loaded text:

- The `SKILL.md` body is the skill instruction text.
- Redaction uses the same conservative secret-line strategy as project instructions.
- Hash original bytes before redaction.
- Trace and CLI JSON must not include the skill body or reference content.

## 7. Reference Semantics

Skill references are read-only files under the selected skill directory.

Allowed reference paths:

- Must be explicitly requested by caller options.
- Must be relative paths.
- Must stay inside the skill directory after lexical and canonical validation.
- Should normally live under `references/`, but v1 may allow any non-hidden regular file under the skill directory except `SKILL.md` if explicitly requested.

Disallowed reference paths:

- Absolute paths.
- `..` traversal.
- Symlinks.
- Non-UTF-8 files.
- Oversized files.
- Files outside the skill directory.
- Files under executable directories such as `scripts/` unless a later policy-backed runtime explicitly allows them.

Reference metadata records path, byte counts, hash, status, redaction status and warnings. Reference content is never written to trace.

## 8. Activation Semantics

Activation is explicit:

- CLI users pass one or more `--skill <skill-id-or-name>` flags.
- Later profile/config activation can reuse the same core request type, but is not part of this slice.
- Missing, invalid, duplicate or skipped skills are reported before provider execution starts.

Core behavior:

- Discover skills through `SkillRuntimePlanner`.
- Resolve requested skills deterministically by id first, then by manifest name.
- Load selected `SKILL.md` text and explicitly requested references.
- Emit a `skill_activated` trace event per selected skill before `agent_run_started`.
- Render one stable-prefix skill system message for all selected skills.
- Include activation metadata in CLI JSON output.

Ordering with project instructions:

1. User goal remains the user message.
2. Project instruction context, when explicitly enabled, is rendered first.
3. Skill context is rendered after project instructions because the user explicitly selected a runtime behavior.
4. Both are stable-prefix context; neither can execute tools or mutate files.

Failure policy:

- Discovery errors caused by unsafe paths fail before provider execution.
- A requested skill that is missing or invalid fails before provider execution.
- A requested reference that cannot be loaded records metadata and fails activation unless the caller explicitly asks for best-effort behavior. v1 should default to fail-closed.

## 9. Protocol Additions

Add provider-neutral metadata. Suggested shape:

```rust
pub enum SkillLoadStatus {
    Loaded,
    SkippedDuplicate,
    SkippedSymlink,
    SkippedOutsideWorkspace,
    SkippedNonUtf8,
    SkippedTooLarge,
    InvalidManifest,
    ReadFailed,
}

pub enum SkillActivationStatus {
    Activated,
    Failed,
}

pub enum SkillRedactionStatus {
    Clean,
    Redacted,
}

pub enum SkillStepKind {
    DiscoverEntrypoint,
    LoadEntrypoint,
    LoadReference,
    RenderContext,
}

pub enum SkillStepStatus {
    Completed,
    Skipped,
    Failed,
}

pub struct SkillReferenceSource {
    pub source_id: ContextId,
    pub path: String,
    pub relative_path: String,
    pub status: SkillLoadStatus,
    pub original_bytes: u64,
    pub loaded_bytes: u64,
    pub sha256: Option<String>,
    pub redaction_status: SkillRedactionStatus,
    pub warnings: Vec<String>,
}

pub struct SkillActivationStep {
    pub step_index: u32,
    pub kind: SkillStepKind,
    pub status: SkillStepStatus,
    pub source_id: Option<ContextId>,
    pub warnings: Vec<String>,
}

pub struct SkillActivation {
    pub task_id: TaskId,
    pub skill_id: SkillId,
    pub manifest: SkillManifest,
    pub status: SkillActivationStatus,
    pub entrypoint: SkillReferenceSource,
    pub references: Vec<SkillReferenceSource>,
    pub steps: Vec<SkillActivationStep>,
    pub warnings: Vec<String>,
}

RunEvent::SkillActivated {
    task_id: TaskId,
    activation: SkillActivation,
}
```

Trace payload must never contain skill body text, reference text, shell commands, generated scripts, provider-private prompts or hidden reasoning.

`RunEvent::kind()` should return `skill_activated`. `RunEvent::task_id()` should return the activation task id.

## 10. Core Additions

Add a focused skill runtime planner in `tessera-core`:

- `SkillDiscoveryOptions`
- `SkillRuntimeOptions`
- `SkillActivationRequest`
- `SkillDiscoveryReport`
- `LoadedSkill`
- `LoadedSkillReference`
- `LoadedSkillSet`
- `SkillRuntimePlanner`

Responsibilities:

- Own all filesystem discovery and reading for skill entrypoints and references.
- Parse `SKILL.md` frontmatter and body.
- Reuse the redaction/hash/byte-limit style established by instruction discovery.
- Build `SkillManifest` values for discovery reports.
- Build trace-safe `SkillActivation` metadata.
- Render skill context text for explicit `AgentLoop` callers.

`AgentRunRequest` should accept an optional `skill_context: LoadedSkillSet`.

`AgentLoop` should:

- emit `skill_activated` events after `instructions_discovered` and before `agent_run_started`.
- include skill context as a system message after project instructions.
- copy activation metadata into `AgentRunSummary` only as safe ids/counts if needed.

CLI/TUI/GUI must not read skill files directly.

## 11. CLI Surface

Add:

```text
tessera skills inspect --workspace <path> [--target-dir <path>] [--json]
```

Text output should show:

- number of loadable skills.
- each skill id/name/description/source path/status.
- warnings.
- no body or reference content.

JSON output should include manifests, source metadata and warnings, with no content.

Extend:

```text
tessera agent run --provider <id> --goal <text> --skill <id> --workspace <path> [--json]
```

Rules:

- `--workspace` is allowed when either `--instructions` or `--skill` is present.
- `--skill` is repeatable.
- Skill activation remains opt-in.
- JSON output includes `skill_activations` metadata and warning count.
- Text output summarizes selected skill ids and statuses without content.

Reference loading can be introduced as:

```text
--skill-reference <skill_id>:<relative/path.md>
```

This must remain explicit and fail-closed in v1.

## 12. Security And Secret Handling

Required guards:

- No default user-global skill discovery.
- No symlink traversal.
- No hidden automatic `scripts/` execution.
- No environment-variable forwarding.
- No network access.
- No arbitrary file read outside workspace or skill directory.
- No content in trace payloads.
- No provider-private prompt text in trace.
- Conservative secret-line redaction before provider context rendering.
- Opt-in live/provider tests only.

The model may see redacted skill text only after explicit activation. The trace sees metadata only.
